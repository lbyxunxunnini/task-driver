# 九项校正改版与实际项目复测

结论：九项方法已落地，但五轮内未达到整体行为验收。已停止协议修正；下文保留明确失败和验证限制。

日期：2026-10-21。当前版本仍为 1.0.7；本轮未提交、推送、发布或同步安装目录。

## 任务与判定边界

用户已逐项确认九项校正，并授权修改、独立子代理审查、随机选取实际项目复测，最多五轮；未通过时停止并提供报告。本报告针对本轮九项校正，不把此前架构改版的结果作为本轮通过证据。修改前内容已另存基线，保留原有未提交变更。

实际项目选用当前 task-driver 的真实 README、文档、检查脚本、版本元数据与项目规则，在隔离副本操作。测试包含文档导航规划、错误定位脚本改动、真实检查进程恢复三类案例；它们来自同一实际项目，不是三个不同仓库。

Claude Code CLI 为 2.1.236；实际 modelUsage 为 DeepSeek v4.1 Flash（含 1m 上下文标记），不能把 CLI 品牌写成 Anthropic Claude 模型验证。用户角色回答采用固定偏好，只回答实际提问；没有把内部评分判据加入测试系统提示。普通项目对话契约保留在真实项目副本内；第五轮复制项目时还带入了本报告的阶段性草稿，lost-return 模型实际读取并提到按此前失败修正。因此存在明确评测材料泄漏，尤其不能将第五轮成功样本解释为对未知案例的独立泛化证明；本测试不是盲测，失败仍保留，不开启第六轮补测。

## 方法改动

| 已确认事项 | 关键修改 | 预期用户可见变化 |
|---|---|---|
| 一问一个独立决定 | discussion 构造选项前确定变量，检查能否分别接受前后半句 | 问得细，但同一轮不用接受整套套餐 |
| 事实范围与反证 | analysis 区分来源覆盖、相关反路径、阻塞与非阻塞未知 | 不把找不到说成不存在，不把条件性规则说成普遍规则 |
| 约束来源 | analysis、templates 记录来源、性质、适用范围 | 直接沿用有效项目规则，不把惯例或建议写成用户要求 |
| 阶段与授权 | 主控区分最终范围、当前环节与当前允许动作 | 方向确定不提前执行；原授权内澄清后继续 |
| 完成时序 | state-recovery 区分文件生成、实际正文交付、宿主同步；复合步骤拆子项 | 文件做好不会提前显示已交付；正文后不能调工具则待自然续接同步 |
| 决定继承 | state-recovery 按来源及现场变化处理恢复 | 不重复质疑有效决定，只重开有真实变化部分 |
| 讨论收口 | discussion 核对覆盖、决定、未知处理路径；按回答关闭排除分支 | 不为穷举制造需求，明确要计划时实际给计划 |
| 委托边界 | discussion 区分局部必要实现与相邻独立取舍，承接整体委托 | 已委托细节自行处理，设计委托不冒充执行许可 |
| 真实恢复 | state-recovery 四种现场结果路由、查询标识、宿主目标恢复入口 | 不重做已完成操作，不因一个未知停止所有独立工作 |

## 证据与限制

原始输入、完整可见消息、工具顺序、模型、文件哈希及实际产物索引：`.task-driver/correction-validation-20261021/`。每个 loop 的协议快照与哈希单独保存。摘要记录：`.task-driver/九项校正-20261021-计划摘要.md`。

恢复使用真实本地进程包装项目的两个实际检查脚本，分别注入运行中、成功但返回丢失、部分失败三种状态；按事件日志核对每步实际次数，不仅匹配文本。它不证明生产网络、扣费、发送、发布等副作用系统的恢复安全。

第一轮脚本修改另在独立副本运行正常路径、围栏内忽略链接、围栏之后缺文件及缺锚点，确认物理行号7/8、原消息和退出码不变；临时目录清理被 CLI 权限策略拒绝，未绕过，保留为限制。

禁止用不同候选的局部通过拼接成最终版本全面通过；没有发生的执行中必要澄清、自然续接状态同步等路径须保留未验证。

## 最后候选的未通过项

1. **提问仍会打包**：`loop5-docs/02/visible.txt` 的 B 选项同时决定双索引、四类速查和模块降为末尾附注；用户可接受第一项而拒绝后两项。
2. **事实与推断仍会混淆**：该回合把使用者“基本不会”打开协议、入口属于噪音称为派生事实，未取得使用者证据。`loop5-checks/01` 只在仓内搜索后推断“无外部兼容风险”，证据范围也不足。
3. **广泛委托后的收口仍不稳定**：`loop5-docs/03` 已收到分组、措辞、说明及版式委托，输出计划时又要求对两个建议点头，并与执行设置一起提问；末句“不特别说明的话我按建议执行”把沉默当同意。业务文件尚未因此实际修改，但措辞违反协议。新增链接与删除规则说明是否属于委托可再判断，不能因此把两个未决事项捆绑或默认通过。
4. **运行中恢复会过早停顿**：`loop5-recover-running/01` 首查后3.94秒实际已完成，模型没有再次核实，约29秒后仍报等待门禁并请求用户决定；将本地测试门禁定性为发布授权无依据。收到下一轮“继续”后才取得结果，不能用此补救抹去首次失败。
5. **宿主状态建立仍晚于实际工作**：`loop5-recover-partial/01` 先 resume、写报告后才创建目标；lost-return 也在写报告后创建，未满足执行前更新状态。

本轮未直接复现“用户回答执行中的必要事实后，模型无缘由停止”这一完全相同路径，也未专门完整覆盖；不能宣称该原始问题关闭。已经出现的是恢复状态误判引发的错误等待。

## 已观察到的改善与适用范围

- 第五轮首次读者提问只有一个决定；第二轮准确保留“只委托名称措辞”的边界，未像第四轮扩张为分组。仍不等于所有选项均独立。
- 脚本案例接受“只加行号”后关闭额外诊断分支，实际输出正式计划；讨论期未修改业务脚本或运行检查，等待明确执行选择。
- 第三、第五轮的交付子项能够保持待交付。第五轮 lost-return 在完整正文与路径交付之后才 completed；partial 在自然续接时核实上轮交付并补记 completed，没有重跑检查。此项有正例，但第五轮存在评测材料可见性限制。
- 第五轮三个进程场景中，最终 contracts 与 metadata 均各执行一次；partial 只恢复缺失步骤，三个业务副本原文件均未改。running 首轮结论与停顿仍失败，所以“无重复执行”不能替代“恢复整体通过”。

## 后续判断

当前不适合宣布问题全部修复、可以稳定开箱即用，或预计平台必达4.8/4.9。本轮没有取得新的 SkillHub 评分。更值得单独讨论的是如何让模型在输出前实际做变量、证据与状态校验，而非继续增加相似禁令；本报告不擅自实施下一轮架构方案。
