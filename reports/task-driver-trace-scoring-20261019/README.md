用户提供 T5.0、R4.4、A4.8、C4.6、E4.7，等权平均确为4.70；但未提供4.8那次的原报告、两次完整权重和评分锚点，无法证明下降0.1是修复导致，也无法直接与本轮4.18比较趋势。

本轮统一要求区分“规则写了”“静态检查通过”“真实行为成功”，4.9锚点要求当前主要使用范围及关键风险有充分实证。原评价中的部分高分理由证据不足或归类不准：

- 中文说明是易用/适配优势，不能直接证明安全和可信任度满分。
- Skill无需额外运行时依赖，不代表宿主和模型无需配置；新增诉求及空项目规则要求联网调查GitHub（SKILL.md:158–160），不能笼统说没有网络问题或全部离线可用。

- 必要的真实用户验收是边界保护，本身不应扣可靠性分。应扣的是可以自行查明却转交用户、重复追问、错误确认状态，以及缺少有效证据却宣布完成。

所以，本轮较低的数字主要反映评价口径与证据权重不同；它不能证明本次单点修复让产品突然退步。也不能反过来说当前稳定性已被证明足够高。

- 不因为追求5分增加认证、术语表、插件、评分系统、必填表单或每轮额外审查。

## 提高到4.9：最多三组动作

### 1. 先补当前版本的执行与复审恢复证据

复用已经存在的Flutter临时副本、两个独立测试文件、标题修改、日志及哈希核对方式，不新增产品流程或测试平台。固定当前候选，分别跑干净正向案例和实际污染材料被拒后的恢复案例；污染材料分别仅含“前次结论”或仅含“执行者自评”，避免两个因素混在一个输入里无法归因。

验收必须直接核对工具事实：用户一次确认后按条件实际并发；两个执行代理没有越界或资源争用；修改后先自检再审；污染输入未产生有效通过；原失败记录存在；主线程自行清理、换新上下文；有效审查读取的版本就是最终产物；此前目标未完成；没有新增用户确认；无后续修改就正常交付。前三次仍无法有效审查时按原上限退出，不无限重试。

影响T/R/E，开发侧工作，不增加用户操作。通过是支持高分的必要证据之一，少量样本不能证明所有情形永不失败。

### 2. 优先复验旧失败，再补最少适配分支

先复用既有复杂测试用例任务，至少两个独立会话，观察首次事实陈述是否与完整工具总数和实际调用链一致、是否仍把“不实际运行”误成删减内容问题、确认状态是否保持。测试过程中不能由操作者提醒正确规则、修改错误产物或删失败样本来制造通过。

然后按实际支持范围少量选测：空项目的新诉求调查；用户关闭子代理时串行；目标工具缺失/失败时降级及中断恢复不重复建任务；缺网不虚构调研；必要验收/授权不足时保持未完成；Codex实际选择器或编号降级。优先复用现有契约和记录格式，不为了覆盖表格逐条制造新流程。

失败先分清当前条款语义漏洞、工具能力差异和实际模型未遵守。仅在证据表明缺口在哪里时提出单点修复；明确条款已经存在仍重复失败，就调查工具/模型适配，不继续换词堆禁令。调整宿主或模型需另行说明影响并取得相应授权，本轮不改配置。

影响T/R/A/E。每类样本的通过范围写清，不将一个宿主的结果外推所有宿主；额外样本数量按风险和实际支持范围决定，没有宣称少量样本足够统计证明4.9。

### 3. 最后再做有证据的文档减负

保持SKILL唯一真源，现有README只保留入口必要信息，展示模板集中在既有模板位置，删除能够确认等价的重复说明；确有入口环境边界缺口时在现有位置补简短说明，不新增文件层级。现有检查只补必要的防回退点，明确静态检查不能判断真实授权和执行时序。

是否精简以代表任务实际必读量、重复确认数和产物完整性判断，不以总字数越少越好。精简前后用同一场景核对计划深度、目标、授权、并发与复审，确认不退步后再保留；没有证据显示负担问题时不急于动已验证内容。

影响C/E，前提是前两组形成稳定行为基线；禁止用删安全边界、删深入分析、减少必要讨论来换token下降。
