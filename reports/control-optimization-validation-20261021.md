# 主控收敛与读取优化：五轮验证报告

日期：2026-10-21。版本保持 v1.0.7，未提交、推送或发布。

## 结论

模块化与去重改动已完成，主控加八模块从 23,952 字符减至 21,761 字符，减少 9.15%。但五轮完整行为验收没有通过，不能宣称流程控制已稳定，也没有证据证明总读取量下降或性能提升。

五次澄清回答后均继续实施，独立功能探针合计 90/90 通过；五次只要计划均未修改业务文件、未索取执行选择。仍有三类流程失败：旧观测错误结束恢复、执行目标入口遗漏或滞后、实际正文前记录已交付。达到五轮上限后停止，没有追加第六轮或继续叠加协议规则。

## 本次范围与实际改动

比较基准是本次开始时的未提交工作区快照，不是 Git HEAD；此前改版及用户已接受关闭的问题保留。

| 位置 | 本次职责调整 |
|---|---|
| SKILL.md | 唯一维护阶段转换、允许动作、输出终点、授权与完成门槛；加入结果驱动转换表；已完成目标重新修改须恢复执行中 |
| 八个职责模块 | 方法、证据及缺口交回主控；删除重复的转换定义，保留具体方法和既有禁止项、反例 |
| 模块路由 | 已完整保留且未变化的内容复用；换环节补缺少模块；链接不递归加载；模板/FAQ按需读取 |
| state-recovery / templates | 同一任务记录保存决定、当前动作、实际回执和恢复标识；合并重复填写字段，保留步骤与目标分别验证 |

没有增加模块、状态维度、审批轮次、读取台账或宿主运行时门禁。分析模块未改变；讨论的精细提问方法、禁止项及反例仍保留，未重开用户已关闭的两类语义问题修复。

除核心减量外，模板从 3,897 减至 3,448 字符，FAQ从 5,615 减至 4,895 字符。字符数量不是 token，也不是实际读取成本。

## 审查顺序与处置

1. 修改完成后，独立子代理对照基线审查。发现精简遗漏“已完成目标重新修改前恢复执行中”，已补回主控，并限定只复用当前仍有效的执行中回执。子代理复核确认此发现关闭。
2. Claude Code 整体逻辑审查收到主控、全部八模块及模板原文，成功返回结果，耗时约197秒。实际后端为 `deepseek-v4.1-flash` / `deepseek-v4.1-flash[1m]`，不是 Anthropic Claude。
3. 核实五项意见后调整三处：讨论收口交回主控；选择器已展示但未答归等待用户；修正验收链接名称并补异常分类入口。另两项已有额度上限或工具降级规则覆盖，未照单重复加规则。审查提出“完成锚点不存在”不实，原锚点实际有效，只修正标签与导航。
4. 冻结协议后完成五轮测试，再由独立子代理核对工具成功回执、真实文件与正文顺序。静态审查完成不等于行为验收通过。

## 测试设计与材料限制

共32次真实 CLI 对话调用：修改前参考7次，优化版五轮共25次；另1次CLI整体逻辑审查不计入复测轮次。所有对话调用正常结束，无超时。每个场景新建独立会话，讨论及澄清的第二轮续接自身会话。

- 讨论：基于实际 CHANGELOG 分析阅读问题；下一轮给出读者、保留历史条目、顶部导航及编辑细节委托，要求只交付计划和目标。
- 澄清执行：实际修改 metadata.sh 的 SKILLHUB_REQUIRED 策略，先问空值语义；用户回答空值非法后沿原授权完成。评测器对产物副本另跑18项功能探针。
- 恢复：真实进程及日志，覆盖仍运行、已完成但回执丢失、syntax成功后metadata前失败。五轮依次为运行中、回执丢失、部分失败、运行中、部分失败。

评测提示与执行者材料不包含评分标准、评测脚本、失败历史或审查结论。目录约束是提示层隔离，不是操作系统沙箱。协议执行通过 Claude Code CLI，未覆盖 Codex / ChatGPT 的实际 UI。

**对照准备失误：** 原计划固定全部业务材料，但最终哈希核验发现候选 snapshot 仍从工作区复制。修改前参考与优化版的 README.md、SKILL.md 不同，CHANGELOG.md、VERSION.md、.skillhub.json、metadata.sh 四文件相同。五个优化版彼此协议与业务材料完全相同。因此前后数据只作描述性参考，不能称严格同条件对照，不能据此归因性能或回归。保留执行时脚本及材料，没有事后改写证据或追加第六轮。

| 2 | 通过 | 继续，18/18 | 回执丢失恢复通过，无重跑 | 澄清失败；恢复通过 | 讨论记录、恢复记录父项 |

### 剩余三类问题

1. **旧观测错误结束：1个案例。** round1-running 的服务status在 `1792540577.688412` 返回running，实际作业在 `1792540580.99556` 完成。模型之后未刷新现场，仍报告检查未开始、没有日志，并将门控文件推断为发布授权。第4轮同场景正确观察到完成；两次结果不同，不能判稳定修复。后台最终成功不替代模型正确续接。
2. **目标入口遗漏或滞后：7/10个实施或恢复案例。** round2/4/5澄清均未建目标即改脚本；round1/3/4恢复未建目标即写报告；round5恢复先成功写报告，才创建目标并置执行中。仅round1澄清、round2恢复、round3澄清满足入口顺序。修改前参考对应4/4满足，但材料存在上述差异，不能据此单独证明改动导致回归；也不能把候选的实际失败忽略。
3. **正文前提前记交付：8/15个候选案例。** 五轮讨论均在正文前记录计划已交付；round2恢复提前勾包含正文交付的父项，子项却仍待交付；round3/4恢复报告提前陈述正文已交付。修改前参考的讨论也有此问题。不能因稍后确实发出了正文，就追认此前状态正确。

这些是已写规则未被稳定遵守的行为问题。本轮没有将它们再改写成更多禁止项，也没有将原先用户接受关闭的问题重新标为待修复。

### 成功证据与未掩盖的失败

- 五轮讨论最终业务副本哈希均未变化，均维护同一份任务记录。
- 五轮澄清最终只修改 metadata.sh，各18项独立探针通过；该结果不等于目标入口通过。
- 所有恢复作业的syntax、metadata各执行一次；partial只resume一次。逐条检查相关Bash后，未发现绕过taskctl直接重复运行检查。
- 修改前参考clarify亦18/18通过；恢复三个分支核心行为通过。control-partial先有完整普通正文，再TaskUpdate completed和勾交付，未误判它为提前完成。
- 模型自测的初次失败保留：第3轮修正非法JSON文案预期，第4轮修正ANSI输出匹配，第5轮修正隐藏文件夹具预期。独立18项探针不依赖模型自述，也不抹掉这些过程失败。
