# 任务驱动

任务驱动以专业分析和共同决策推进复杂任务：先讨论，再形成计划与结果目标，确认后执行；始终完成主模型审查与修复，按设置追加独立复核，满足全部完成条件后收口。

## 30 秒选择器

使用任务驱动：

- 目标、范围或验收不清楚。
- 涉及多个文件、模块或外部系统。
- 涉及权限、费用、发布、分支、提交、合并、删除或覆盖重要文件。
- 用户要求先计划、先澄清或完整推进。

不使用任务驱动：

- 简单问答。
- 只需要执行一个安全命令。
- 单文件低风险小改动，且用户明确要求直接改。

谨慎使用：

- 用户要求立即执行，但任务存在风险动作时，先确认授权和最终验收目标。
- 任务看似很小，但失败会影响生产、数据、费用或不可逆状态时，按任务驱动推进。

选择器只决定是否采用 Skill，不增加用户阶段。即使不采用，也不得伪造验收目标或越权执行；额外动作必须先取得授权。

## 能力边界与环境适配

本 Skill 是中文 Markdown 协议，不内置模型服务或固定业务 API。模型、工具、网络、账号和设备访问能力由宿主及任务环境提供；国内能否完成具体任务，取决于这些能力是否实际可用，不能仅凭协议可在本地读取就承诺全流程可用。

以下只汇总现有处理路径，完整约束仍以主协议为准：

| 能力 | 宿主或环境需要提供什么 | 缺失或不可用时的现有路径 |
|---|---|---|
| 原生提问 | 当前会话实际开放、允许调用的工具及其 schema、模式 | 非交互、工具不可用、调用失败或已知必要内容仅留在折叠过程区时，说明限制并在最终答复使用编号选项；禁止擅改模式或声称已弹窗。关闭、预选、超时或无回答均不是授权。见[选择器适配](references/faq.md#原生选择器怎样使用)。 |
| 目标管理 | 聚合目标能力，或 `TaskCreate`、`TaskList`、`TaskUpdate` 及可读取的 schema | 按[宿主目标工具协议](SKILL.md#宿主目标工具协议)核对 schema、处理参数错误；目标工具不可用时自动降级到计划工具（如 `update_plan`）原样跟踪验收目标，两类工具均不可用才维护对话内轻量目标。涉及覆盖旧目标、改变范围或丢失状态时必须先让用户选择，禁止重复创建。 |
| 网络与资料 | 联网调研工具、可访问的资料及目标外部服务 | 必须用自身知识深入分析，能联网时结合搜索补充；不能联网时继续专业分析，只对无法核实的外部事实说明缺口，不编造搜索结果。执行所必需的外部服务不可用且没有替代路径时标记受阻，不机械重试。见[调研要求](SKILL.md#单事项讨论协议)和[异常分类](SKILL.md#异常分类)。 |
| 账号与权限 | 对当前动作有效的权限、凭据及必要费用授权，以及宿主实际可用的访问工具 | 已知无访问工具且没有可靠替代路径时，按[异常分类](SKILL.md#异常分类)说明受阻，禁止要求用户再次确认已知限制；补齐凭据不能补足访问工具。仅缺凭据或授权时，立即停止相关执行，请求用户授权或决定，不消耗修复次数；已有授权必须复用。真实账号中的结果无法可靠验证时，先完成可做检查，再按[用户验收补位](SKILL.md#用户验收补位)处理。 |
| 设备与主观体验 | 实际设备、可访问的界面或人的体验反馈 | Agent 必须先完成自己能做的检查，再提供具体验收步骤、预期结果、通过条件和反馈要求；反馈前不得标记达标。用户无法完成必要验收且没有其他可靠证据时标记受阻。见[用户验收补位](SKILL.md#用户验收补位)。 |

实际验证范围以对应记录为准，不把单一环境的成功外推到所有宿主；本 Skill 不能补足宿主缺失的访问能力。

## 核心链路

完整条件与返回路径见[核心链路](SKILL.md#固定链路)，执行时以该处为准。

这条链路分别回答：

- 为什么做、关键取舍是什么：逐项讨论。
- 做什么、准备怎样实施：计划。
- 做到什么结果才算完成：最终验收目标。
- 怎样持续做到目标：主模型审查—打回—修复—重新审查，必要时追加独立复核。

## 使用方式

当用户消息以以下任一形式开头时，进入任务驱动：

```text
tdr- ...
task-driver ...
/task-driver ...
```

例如：

```text
tdr- 先和我讨论登录页按钮错位的修复范围，再形成计划并执行
```

## 最短完整流程

下面展示范围和关键方案已明确、完成标准无待决事项、授权与重要风险问题已解决时的合并路径；不满足[合并条件](SKILL.md#计划和目标合并展示条件)时，先讨论缺口，再分别确认。

```text
用户：tdr- 先讨论登录按钮错位的修复，再给计划。只修位置，不统一其他按钮样式。

助手：调查现有布局，逐项讨论必要取舍。与用户确定：按钮在桌面居中、窄屏不溢出，保留现有样式和点击行为；仅修改本地文件，不提交或发布。

用户：生成计划。

助手：
计划草案
1. 修复登录按钮位置
   已确认：桌面居中、窄屏不溢出；保留现有样式和点击行为，仅修改本地文件。
   实施方案：调整表单容器的对齐和宽度约束，复用现有按钮；检查桌面与窄屏布局及点击行为。

验收目标草案
1. 登录按钮在桌面居中、窄屏不溢出，原有样式和点击行为不变。

选择执行即确认以上计划、目标、范围及子代理设置：
1. 执行，开启子代理：按协议判断是否可并发实现，并追加独立复核，增加时间与资源消耗。
2. 执行，不开启子代理（推荐）：范围集中，由主模型执行并完成审查修复闭环，流程更轻。
3. 不执行，继续讨论：暂不修改，调整计划或目标。

用户：执行，不开启子代理。

助手：原样跟踪目标并执行，完成主模型审查修复和必要交付；具备有效验收证据后同步完成。若无法检查实际布局，先说明已做检查及用户验收步骤，反馈前保持未完成，不重复请求执行授权。
```
