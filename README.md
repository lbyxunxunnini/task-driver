# 任务驱动

任务驱动面向复杂任务，仅由用户显式调用。禁止主动介入其他任务。先取得任务目标，复述理解并等用户认可，再调查、分析和讨论，再按下文流程展示正式计划与验收目标，取得执行授权后实施。必须完成主模型审查与必要修复，按设置追加独立复核，并在满足完成条件后收口。

## 30 秒选择器

适合用户调用任务驱动的情况（不作为自动触发条件）：

- 目标、范围或验收不清楚。
- 涉及多个文件、模块或外部系统。
- 涉及权限、费用、发布、分支、提交、合并、删除或覆盖重要文件。
- 用户要求先计划、先澄清或完整推进。

通常不必调用，按宿主常规方式处理：

- 简单问答。
- 只需要执行一个安全命令。
- 单文件低风险小改动，且用户明确要求直接改。

谨慎使用：

- 用户要求立即执行，但任务存在风险动作时，必须先确认对应授权和最终验收目标。显式调用 Task Driver 后，必须另遵守[入口规则](SKILL.md#接到任务后的第一步)及[执行授权](SKILL.md#展示与确认策略)。
- 任务看似很小，但失败会影响生产、数据、费用或不可逆状态时，按任务驱动推进。

选择器只决定是否采用 Skill。禁止因此增加用户阶段。无论是否采用，都禁止伪造验收目标或越权执行。额外动作必须先取得授权。

用户显式调用后必须沿用完整流程，禁止另设轻量模式。

## 能力边界与环境适配

本 Skill 是中文 Markdown 协议，不内置模型服务或固定业务 API。模型、工具、网络、账号和设备访问能力由宿主及任务环境提供。国内能否完成具体任务，取决于这些能力是否实际可用。禁止仅凭协议可在本地读取就承诺全流程可用。

以下仅汇总现有处理路径。执行时必须遵守主协议的完整约束。

| 能力 | 宿主或环境需要提供什么 | 缺失或不可用时的现有路径 |
|---|---|---|
| 原生提问 | 当前会话实际开放、允许调用的工具及其 schema、模式 | 非交互、工具不可用、调用失败或已知必要内容仅留在折叠过程区时，必须直接在最终答复使用编号选项。禁止擅改模式或声称已弹窗，也禁止将关闭、预选、超时或无回答视为授权。见[选择器适配](references/faq.md#原生选择器怎样使用)。 |
| 目标管理 | 聚合目标能力，或 `TaskCreate`、`TaskList`、`TaskUpdate` 及可读取的 schema | 必须按[宿主目标工具协议](references/execution.md#宿主目标工具协议)核对 schema、处理参数错误。宿主 Goal 可用时必须查询并复用或创建。降级必须有实际工具或宿主证据证明不可用，禁止因模型不确定或用户未明确请求而自行降级。确实不可用时，必须说明原因并征求用户是否接受计划或对话编号跟踪。涉及覆盖旧目标、改变范围或丢失状态时必须先让用户选择。禁止重复创建。 |
| 网络与资料 | 联网调研工具、可访问的资料及目标外部服务 | 必须用自身知识深入分析。能联网时必须结合搜索补充，无法联网时必须继续专业分析，并把缺口说明限定在无法核实的外部事实。禁止编造搜索结果。执行所必需的外部服务不可用且没有替代路径时，必须标记受阻，禁止机械重试。见[调研要求](references/discussion.md)和[异常分类](references/review.md#异常分类)。 |
| 账号与权限 | 对当前动作有效的权限、凭据及必要费用授权，以及宿主实际可用的访问工具 | 已知无访问工具且没有可靠替代路径时，必须按[异常分类](references/review.md#异常分类)说明受阻。禁止要求用户再次确认已知限制。补齐凭据不能补足访问工具。仅缺凭据或授权时，必须立即停止相关执行并请求用户授权或决定，禁止消耗修复次数。已有授权必须复用。真实账号中的结果无法可靠验证时，必须先完成可做检查，再按[用户验收补位](references/verification.md#用户验收补位)处理。 |
| 设备与主观体验 | 实际设备、可访问的界面或人的体验反馈 | Agent 必须先完成自己能做的检查。仍需用户验收时，必须提供具体验收步骤、预期结果、通过条件和反馈要求，反馈前禁止标记达标。用户无法完成必要验收且没有其他可靠证据时，必须标记受阻。见[用户验收补位](references/verification.md#用户验收补位)。 |

实际验证范围必须以对应记录为准。禁止将单一环境的成功外推到所有宿主。本 Skill 不能补足宿主缺失的访问能力。

## 核心链路

执行时必须遵循[核心链路](SKILL.md#固定链路)的完整条件与返回路径。

这条链路分别回答：

- 为什么做、做成什么样、有哪些用户取舍：全面分析后必须先复用已有决定与现有机制。同一场景可以整体讨论具体建议，必须将提问限定在必要的用户取舍。
- 做什么、准备怎样实施：计划。
- 做到什么结果才算完成：最终验收目标。
- 怎样持续做到目标：主模型审查—打回—修复—重新审查，必要时追加独立复核。

## 使用方式

执行分工由主控在授权内按需决定，独立复核另按用户选择。收到“子代理你决定”等覆盖复核的有效委托时，主控按收益和宿主能力决定。App、H5 由主控分支实施并验收，开启的子代理只做收尾代码静态复审。

当用户消息以以下任一形式开头时，必须进入任务驱动。

```text
tdr- ...
task-driver ...
/task-driver ...
```

例如：

```text
tdr- 先和我讨论登录页按钮错位的修复范围，再形成计划并执行
```

## 最短完整流程

缺目标时先问想解决什么。已有目标时复述痛点、使用过程和期望结果，等待首次理解确认；后续明确且相容的补充直接承接，仅对影响交付的歧义或冲突澄清受影响部分。理解确认后，首轮方案讨论在正文说明整体思路，按优先级列出全部待决项。讨论图和要求表在内部维护，默认不附摘要链接；用户明确要看图时，在正文展示当前图。每次答复保留来源，沿依赖只重算受影响部分。调查和分析后，有待决项时必须先核实可查事实，每轮只问优先级最高的一项。收到答复后必须重新核对剩余待决项。没有待决项时，在正文逐项说明每条要求怎么做、怎么验，再实际询问用户是否结束讨论并开始展示正式计划与验收目标。必须等到用户对该收口问题明确作出肯定答复，再按[展示与确认策略](SKILL.md#展示与确认策略)同轮展示正式计划与验收目标。展示后必须另行取得针对已展示内容的明确执行授权。展示后的同一条用户回复可以同时确认计划、目标与执行方式。图表的完整写法见[摘要示例](references/templates.md#讨论图表示例)。

```text
用户：tdr- 先讨论登录按钮错位的修复，再给计划。只修位置，不统一其他按钮样式。

助手：你希望用户打开登录页时能看到位置正确的登录按钮，改动只涉及这个按钮的位置。我理解得对吗？
用户：对。

（随后调查现有布局，说明整体思路和全部待决项，逐项讨论并更新同一摘要。下面接收口回合。）

助手：
• 桌面居中、窄屏完整可见：调整表单对齐与宽度，核验时在两个已约定的屏宽核对按钮位置和边界。
• 保留样式和点击行为：复用现有按钮，核验时对照原样式并点击验证原登录动作。
• 仅修改本地登录布局：只改登录布局，核验时核对工作区差异和操作记录。

是否结束讨论并开始展示正式计划和验收目标？

用户：可以，展示计划和目标。

（按同一摘要的流程节点编排步骤，按要求表的通过条件生成目标。）

助手：
计划草案
1. 修复登录按钮位置
   已确认：桌面居中、窄屏不溢出；保留现有样式和点击行为，仅修改本地文件。
   实施方案：调整表单容器的对齐和宽度约束，复用现有按钮；检查桌面与窄屏布局及点击行为。
   执行步骤：S1 [pending] 调整位置与宽度约束；S2 [pending] 检查两种布局并记录证据。

验收目标草案
included（纳入验收）：
G1 [changed] 登录按钮在桌面居中、窄屏不溢出，原有样式和点击行为不变；来源：用户要求只修登录按钮。

excluded（明确排除）：
E1 其他按钮样式统一修改；来源：用户要求只修登录按钮。

请确认计划和目标内容。

内部状态必须同时把当前 included/excluded 快照写入 `goal_scope_baseline`。用户后续改变目标时，必须使用旧快照识别范围变化。

用户：确认计划和目标。

助手：计划与目标内容均已确认，现在请选择执行方式：
1. 执行，开启独立复审：主控自检后追加独立复审，增加时间与资源消耗。
2. 执行，不开启独立复审（推荐）：范围集中，由主控自检、复查和修复。
3. 不执行，继续讨论：暂不修改，调整计划或目标。

用户：执行，不开启独立复审。

助手：原样跟踪目标并执行，完成主模型审查修复和必要交付；具备有效验收证据后同步完成。若无法检查实际布局，先说明已做检查及用户验收步骤，反馈前保持未完成，不重复请求执行授权。
```


## 构建发布包

在本项目 Git 工作区运行 `bash scripts/build-package.sh`，生成独立临时目录并检查包内文档链接、对话契约、状态控制测试和版本元数据。输出目录可用于后续发布；此命令不提交、不上传。

包包含 `SKILL.md`、`README.md`、`VERSION.md`、`.skillhub.json`、`CHANGELOG.md`、`references/`、`scripts/` 和 `tests/`。脚本复制这些范围内已跟踪文件的当前工作区内容及打包脚本自身，不包含本地规则、任务记录或演示。新增配套文件必须先纳入 Git 跟踪，再构建。必须检查实际包目录，禁止用源码检查代替。
