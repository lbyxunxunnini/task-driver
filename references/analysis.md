# 调查与分析

输入：最新请求、已知决定、可访问材料和环境能力。输出：任务理解、事实与来源、可行方案及其后果、待用户决定事项与依赖。事实不足时必须先调查。必须把确需用户提供的事实或作出的选择交给讨论，禁止把专业分析转嫁给用户。

## 分析的组织

必须沿“用户目标 → 实际使用过程 → 方案及后果 → 待决事项”组织分析，并说明每个问题与目标的关系及不同答案的实际影响。最终范围、当前阶段、允许动作由主控区分。禁止把当前不运行支付视为删除支付覆盖，或把旧系统具备的功能自动纳入恢复目标。

### 接手任务，形成做法

接手任务必须先从用户原话、已有决定和材料辨明交付物供谁使用、要完成什么、怎样判断做成了。禁止把手段当成结果。不同解释会导向不同交付时，必须先用材料排除；仍无法区分时必须尽早问方向，无需预先设计两套方案。目标清楚时必须直接承接。尺度宽泛时，必须用有依据的可接受差异与不通过情形说明建议边界，禁止冒称用户已确认。

必须沿使用者从起点到结果的路径拟定做法，核实决定成败的步骤：在给定条件下，谁能做哪个动作、会得到什么、后一步能否接上？材料只有名称或终态时，必须先找实际行为、前提或实例。禁止把其他人才有能力或权限完成的动作算给当前使用者。方案必须沿用已证实有效的做法，按限制约束承诺，原路径不可行时查找替代路径。禁止反复调查对当前决定已充分的事实，或为凑齐清单制造边界情形。

### 从做法选出下一问

必须先核实可查事实、沿用适用规则和有效决定，在授权内处理专业细节。同一场景有足够依据时，必须先形成一套可评审建议，说明做法、结果、适用条件和验收方法，标明沿用的依据、建议和未决缺口。列为待决前，必须说明哪项当前要求无法凭现有事实、适用规则或授权内判断满足，或哪项交付偏好确需用户选择。禁止以可选增强或待整体评审的建议阻塞计划。多个事项待决时，必须优先处理会改变后续设计的事项；会改变整套方案的前提必须优先核实，确需用户提供时直接询问。问题必须按[讨论模块](discussion.md)组织。

### 回答后重算下一步

必须先按[回答后的推进](discussion.md#回答后的推进)识别答复对象和范围，再把答复代回方案，核对哪些步骤要改、哪些问题已消失或仅部分解决、哪些依赖现可判断。补查必须限于受影响的事实。答复揭示会改变目标或交付的分歧时，必须先处理该分歧，再讨论依赖它的偏好与细节。仍需用户作决定时，必须从更新后的做法选出下一问；否则必须交回主控按[入口](../SKILL.md#接到任务后的第一步)处理。禁止沿用失效的问题清单或只记新决定而原样交出旧计划。

### 事实推断与约束

必须先限定证据实际证明的对象、范围、口径和条件，再形成结论。推荐前必须检查任务内是否存在使结论不成立的相关路径；发现反例时，必须保留成立条件并给出核实路径。禁止用“可能”替代逻辑修正或扩展无关假设。

| 反例 | 缺失依据 | 正确承接 |
|---|---|---|
| 新机取消定时，旧机上线也不会重复构建 | 新机手动与旧机定时仍可能重叠 | 结论必须限于新机不再由该定时启动。仍必须核实旧机是否可能上线及其他触发路径 |
| 入口不好找，所以现有文档没有该入口 | 可发现性问题不等于缺失；必须核对实际索引与链接覆盖 | 找到已有入口就必须评估位置与说明，禁止宣称不存在 |
| 单次构建 4GB，保留 30 次，所以归档已占 120GB | 单次占用不等于归档大小，保留上限不等于实际份数 | 必须保留原口径，需要时核实实际文件大小与份数 |

必须按内容的来源与性质约束方案，禁止把原文的适用范围理解得更宽或把约束理解得更严：

| 内容性质 | 使用边界 |
|---|---|
| 已核实事实或当前做法 | 可作分析依据；现有五列表格不等于禁止增加列 |
| 有效项目规则、已确认方案、用户明确要求 | 必须核对来源、适用范围、时效与冲突后直接沿用，禁止重复索取同一确认；“保持公共接口兼容”不等于禁止内部重构 |
| 有证据的技术限制 | 必须用于约束当前实现；环境或方案变化时必须重核，禁止直接认定限制永久有效 |
| 委托内模型决定 | 在委托范围内可落实；必须保留委托来源并区分模型据此作出的决定 |
| 模型偏好、建议、待证推断 | 禁止作为已定约束；更新其性质前必须取得适用确认、有效委托或新证据 |

判断是否需要用户介入时，必须单独核对依据。观测到文件、状态或名称只证明它存在；禁止据名称推断发布权限、用户意愿或业务禁令。用途未明时必须保留未知并先用已授权的只读查询，禁止凭未核实的解释新增授权障碍。仓内未找到使用方时，结论必须限定在本次检索范围内，禁止外推为没有外部兼容风险。

必须分别保留推荐所依赖的关键断言中“来源实际证明的内容”和“模型对它的解释”。声称某格式不可替代或某情况必然失败前，必须核对实际条件、替代分支和适用对象。解释未核实时，推荐必须限于来源已证明的内容，禁止用推断约束后续方案。检查器接受多种标题形式时，结论必须只列标题必须满足的已核实条件。禁止从固定产品名推断唯一的分发渠道。

必须记录依据的内容、来源、性质和适用范围。发现真实规则冲突，或时效疑点影响方案时，必须指出具体问题，禁止自动覆盖。禁止把推断当成现场事实，或对工具未确认的环境能力直接判为缺失或可用。没有可靠依据时禁止编造精确数量或效果保证。

未知条件会改变范围、代价、方案或通过条件时，必须先自行核实可查事实；仍无法核实且确需用户输入时，必须作为独立问题讨论。其他未知若有可行的后续核实路径，必须记录后继续，禁止因此中断当前讨论。环境能力不足时，必须提出受限交付建议或说明阻塞条件，禁止自行用工具方便产出的格式替换用户目标。

### 按任务类型调研

必须先用专业知识从最终产物的用途和体验推演必要要素、关联及质量判据，并核对用户提供的材料和原有成果，禁止只拆成基础参数问答。需要核实外部事实、方法或成熟方案时，必须按领域、问题及用户或宿主要求选择资料；用户明确要求联网或适用规则要求调研时必须遵从。资料不可获取时，必须用已有专业知识继续分析、给出具体建议并说明哪些外部事实未核实。禁止编造调查结果或仅为形式重复搜索；适用性已核实的可靠旧资料必须复用。

调整、升级或重做已有成果时，必须先读适用规则与可靠摘要，再沿目标和实际使用过程核查相关原有内容、使用或呈现方式及关联影响，形成有来源的现状。必须查找与目标相关但尚未提出的行为和状态；复杂时必须沿依赖扩展，禁止机械扫描全部材料。必须区分已核实的现状、用户明确的新要求和模型提出的候选方案，并比较影响当前决定的变化。禁止把现状自动记成用户决定保留。用户明确要求保留时，必须把该范围内已核实的具体内容或行为作为约束，记录用户要求和现状来源，禁止冒称逐项确认。无法核实的内容必须标为未知。软件任务按需核对相关入口、实现、配置和行为；摘要与现场冲突时必须以核实后的事实为准。

资料较多且可独立调查时，必须按[子代理管理](subagents.md#选择执行方式)判断是否委派只读调查。委派内容必须限于调查问题、已定约束、相关材料和读取边界。调查结果必须交回影响方案或验收的事实与原文位置、适用条件及例外、调查覆盖和未知事项。主模型必须核对关键结论的原文，复用其余适用发现，再形成设计并筛选待决项。材料和范围未变时必须复用有效调查。

新增诉求必须先查清已有条件和能力缺口；空项目或开放需求必须先分析场景与可行路径，禁止因没有代码就只发需求表单。确需比较成熟方案时，必须按领域核实其能力、适用条件、限制与代价；软件方案可查官方文档和实际实现，其他领域使用对应原始资料和方法。搜索必须围绕当前问题，禁止预设仓库数、用星数或搜索摘要替代适配性判断，或复制未经审查的代码。

形成判断前必须能说明实际问题、可行方向、依据、主要限制和用户未决事项。禁止把专业建议记为用户决定或把可自行完成的调查和分析转交用户。

### 全面展开与逐项深挖

下列视角可用于发现当前目标内的遗漏。禁止整份发给用户作问卷，或将它们设为每轮必做的检查。

| 分析角度 | 领域推演 |
|---|---|
| 目的与场景 | 谁在何时使用，实际过程是什么 |
| 结果与质量 | 交付内容、体验、审美、成功与失败表现 |
| 范围与保留 | 改什么、保留什么，旧数据与产物如何承接 |
| 完整过程 | 输入到结果的依赖、状态与独立选择 |
| 异常与边界 | 缺失、失败、重复、中断、取消的实际影响 |
| 条件与代价 | 环境、时间、费用、权限；哪些事实应自行核实 |
| 交付与后续 | 获取、验收、交接、复用中与本次目标有关的选择 |

例如创作要关联情绪、构图与可感知效果；环境恢复要结合真实配置推演启动后的行为。禁止把领域清单当作所有任务的固定需求；恢复范围按[分析的组织](#分析的组织)核对。


## 交接

必须交接当前做法及改变做法、限制承诺或仍需用户决定的关键依据，禁止另建表单。计划必须承接同一方案，并保留内部实现；决定使用成败的行为、结果及适用条件必须进入[验收目标](goals.md)。仍需取舍时必须交给[讨论](discussion.md)；用户明确委托且范围完整时必须交由主控按[入口](../SKILL.md#接到任务后的第一步)处理。任务类型案例见[场景](scenarios.md)，禁止把案例参数当作通用默认值。
