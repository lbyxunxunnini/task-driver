# 计划设计

输入：已确认需求、决定及委托范围、事实和依赖。输出：具体实施方案与影响范围。未决事项会改变用户选择时，必须交回主控，禁止以计划草案代替讨论。首次正式展示必须遵循[主控入口](../SKILL.md#接到任务后的第一步)；展示组织和另行确认执行按[主控](../SKILL.md#展示与确认策略)处理。

## 输出计划

计划必须说明做什么、怎样实施和影响哪里。默认必须在对话中展示，禁止另行落盘；获准记录时按[计划的完整程度](#计划的完整程度)保存。

必须根据已决项和有效约束生成方案，逐项沿用适用的已定范围，禁止因细节委托自行缩小范围。缺失事实能查必须先查，无法核实时必须按影响保留缺口。发出前必须逐项核对承诺对象、拟做操作和验证口径，确保三者一致。

- 会改变用户结果、范围、费用或风险的操作，必须注明所依据的决定、规则或委托内决定。依据不明时必须退回对应决策项；必要内部实现必须自行确定。
- “保留”必须对应具体对象。保留条目内容、保留标题原文、保留链接可达性是不同承诺；允许改标题时禁止同时承诺全部原文逐字不变，合并章节时禁止同时承诺章节数量不变。必须沿用用户的原约束并验证相应对象，禁止自行扩大承诺。
- 操作与承诺冲突时，必须先修正方案；需要用户改变要求时必须回讨论。非阻塞的事实缺口必须列为核实步骤，禁止把解释尚未核实的限制写成硬约束。

会改变使用者职责、投入、操作流程或交付结果的选择，必须按实际影响作为取舍说明，禁止仅称作“实现细节”便视为已委托。用户认可方向时，确认必须限于该方向实际包含的内容，禁止自动扩大为此前全部建议。已有有效委托时，必须自行决定并保留来源。同一场景的必要取舍可随完整方案一起讨论，禁止为此新增逐参数确认；候选验收条件必须按[最小必要目标](goals.md#最小必要目标)核对来源和必要性。

正式计划必须提供按顺序编号的 `plan.steps`。每步必须记录稳定 `id`、动作 `action`、状态 `status` 和所需验证证据。从 pending 进入其他状态时，目的状态必须为 in_progress、done 或 blocked。前项未完成时禁止把后项标记为 done，禁止把计划展示当作步骤完成。

编排计划中的检查动作时，必须按[取证顺序](verification.md#验证前限定范围)核对实际依赖。

必须按主控规则组织计划末尾的展示与确认。新发现用户必须作出的取舍时，必须交回讨论；按请求交付缺口稿时，必须标明未完成之处并按[主控阶段转换](../SKILL.md#阶段转换)处理。委托内决定必须说明来源，禁止再次索取确认。

顶层必须按已确认的独立需求或问题组织，合并或拆分必须说明来源和原因。每项必须包含 `### 已确认` 和 `### 实施方案`。`### 已确认` 必须限于用户决定或既有规则，并标明来源；委托内自行决定必须写入 `### 实施方案` 并标明委托来源。预期变化、涉及位置和内部验证按需补充，简单任务可省略。表格必须限用于短字段比较，禁止塞入完整方案。格式见[计划草案模板](templates.md#计划草案展示模板)。

### 实施方案规则

| 要求 | 必须动作或限制 |
|---|---|
| 具体方法 | 必须说明核心机制、作用边界和关键约束；“完整、全面、深入”必须落实为覆盖方法和核对依据，禁止用“分析、编写、完善、检查”冒充方法 |
| 实施细节 | 禁止展开逐行代码、完整命令或文件流水账；文件、测试、文档和版本必须放入对应事项的涉及位置或内部验证 |
| 跨事项公共工作 | 可放入非编号的“统一实施工作”，禁止另计为需求或问题 |
| 表达 | 必须使用任务目标、计划事项、实施方案等通用称谓，禁止预设任务必为代码改造 |

## 方案与详细设计核对

用户只要求详细设计时也必须使用本节核对。禁止以设计替代正式计划，或因交付设计而改变当前环节、计划格式或执行授权。用户要求先看且仍有实质缺口时，必须交付标明缺口的设计稿，禁止声称全部决定已闭合。

必须复用[分析模块](analysis.md#事实推断与约束)的反例判断，选择影响结果的具体情形，串联触发条件、处理、结果和验证口径，检查限制叠加、失败或重跑是否改变结论。必须核对方案正文、示例、待定事项和验收用例中的对象、时点、数量、顺序及前提是否符合已定规则；不同情形可用不同输入。必须交代整体结果成立的条件或保留未解决缺口，禁止以局部机制保证整体结果或承诺超出机制能保障的验收结果。未知现状或决定必须标为待核实、待决定或建议，说明流程及验收依赖的假设。禁止写成已确认，或为自查制造无关问题及新增确认轮次。

## 正式计划的覆盖核对

必须先从最新有效的用户要求、决定和材料中独立列出必须保留或实现的关键行为，再对照待发送的计划与验收条件。每项必须核对依据、实际触发动作或条件及可观察结果。简单交付必须以实际检查动作及预期产物为一项。必须按场景核对操作与结果，禁止只用上位功能名概括可独立失败的行为。例如连续滑选歌词和拖动音高分别保留其操作与可观察变化。必须反向核对新增入口、失败路径及外部条件的实际范围依据。缺覆盖必须补正文，新增范围需要用户决定时必须交回讨论。

首次正式展示或局部修订前，必须用[正式计划正文检查](workflow-control.md#正式计划正文检查)对照来源和实际正文，内部清单必须限于本次展示中会改变交付范围或通过结论的关键承诺。同一次观察可一并证明的细节可合并，无需为每个控件、样式和中间状态单列。必须依据原始来源并复用本轮已有材料，禁止另建文档或向用户交付内部清单。核对通过后必须发送实际检查过的正文，并按原规则记录展示与确认。

## 讨论并确认计划

修改时必须更新同一份有效计划；已展示的计划默认必须只返回新增、修改或删除的条目及其新内容与受影响的关联项，禁止重列未变化部分。用户要求完整版本时必须全部展示。必须保留未受影响的决定和授权，并交回新发现的决定缺口。确认、目标展示和执行转换必须遵循[主控阶段转换](../SKILL.md#阶段转换)，禁止另定确认流程。

## 计划的完整程度

计划必须说明实现机制、先后依赖、主要风险和失败处理，以及每项如何验证。不适用的内容可省略，省略会影响理解或验收时必须说明原因。禁止为套模板增加无关工作，或用“分析、实施、检查”代替可执行的方法。长计划可拆执行步骤，但顶层必须仍对应用户需求，禁止把步骤当新增最终目标。

需要评估子代理分工时，必须读取或复用[子代理管理](subagents.md#选择执行方式)，将执行方式、依据和拟分派边界写入实施方案。禁止以编制分工方案充当分派授权。

长计划的首次保存、编制中更新和执行前核对，必须按[记录与恢复](state-recovery.md#变化与保存时机)处理。正文计划必须与记录中的有效计划一致；改变方案时，必须交回主控判断需要重核的决定、授权和证据。
