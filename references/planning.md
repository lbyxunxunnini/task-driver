# 计划设计

输入：已确认需求、决定及委托范围、事实和依赖。输出：具体实施方案与影响范围。未决事项会改变用户选择时交回主控，不能用计划草案代替讨论。展示合并和执行确认由[主控](../SKILL.md#展示与确认策略)决定。

## 输出计划

目的：说明做什么、怎样实施、影响哪里。计划默认只在对话展示，不另落盘。

从讨论模块的已决项和有效约束生成方案。发出前按“承诺对象 → 拟做操作 → 验证口径”核对每项，三者必须一致：

- 会改变用户结果、范围、费用或风险的操作，注明所依据的决定、规则或委托内决定；依据不明才退回对应决策项，必要内部实现自行确定。
- “保留”要对应具体对象。保留条目内容、保留标题原文、保留链接可达性是不同承诺；允许改标题时不能同时承诺全部原文逐字不变，合并章节时不能同时承诺章节数量不变。沿用用户原约束，不自行扩大承诺，再用检查验证该对象。
- 操作与承诺真正冲突时先修正方案；若需用户改变要求才回讨论。非阻塞事实缺口列为核实步骤，不把解释未核实的限制写成硬约束。

计划末尾由主控按当前请求组织展示与确认。发现新的待用户取舍则返回讨论或标注未完稿；已委托事项由模型决定并说明来源，不再求用户点头。

顶层按已确认的独立需求或问题组织，合并或拆分必须说明来源和原因。每项必须包含 `### 已确认`、`### 实施方案`；预期变化、涉及位置、内部验证按需补充，简单任务可省略。表格仅用于短字段比较，不强塞完整方案。格式见[计划草案模板](templates.md#计划草案展示模板)。

### 实施方案规则

| 要求 | 必须动作或限制 |
|---|---|
| 具体方法 | 说明核心机制、作用边界和关键约束；“完整、全面、深入”必须落实为覆盖方法和核对依据，不能用“分析、编写、完善、检查”冒充方法 |
| 实施细节 | 不展开逐行代码、完整命令或文件流水账；文件、测试、文档、版本归对应事项的涉及位置或内部验证 |
| 跨事项公共工作 | 可放入非编号的“统一实施工作”，不另计需求或问题 |
| 表达 | 使用任务目标、计划事项、实施方案等通用称谓，不预设任务必为代码改造 |

## 讨论并确认计划

修改时更新同一份有效计划；返回修订内容和新发现的决定缺口。确认、目标展示和执行转换统一按[主控阶段转换](../SKILL.md#阶段转换)，不在本模块另定确认流程。

## 计划的完整程度

计划应说明实现机制、先后依赖、主要风险与失败后的处理，以及每项怎样得到验证。不按模板制造无关工作，不以“分析、实施、检查”三个动词代替可执行的方法。长计划可拆执行步骤，但顶层仍对应用户需求；步骤不是新增最终目标。

需要评估子代理分工时读取或复用[子代理管理](subagents.md#选择执行方式)，把执行方式、依据及拟分派边界纳入实施方案；编制分工方案不等于已取得分派授权。

长计划的首次保存、编制中更新与执行前核对，统一按[记录与恢复](state-recovery.md#变化与保存时机)处理。正文计划与记录中的有效计划保持一致；改变方案时由主控判断哪些决定、授权和证据需要重新核对。
