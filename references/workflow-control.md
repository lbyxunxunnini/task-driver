# 轻量状态检查

主控在对话或[唯一任务摘要](state-recovery.md#何时建立记录)中维护原目标、当前环节、已决定事项及来源、未决事项、下一动作和授权。普通讨论在上下文维护状态；达到[记录条件](state-recovery.md#何时建立记录)后，建立或复用同一任务摘要并增量维护问题和回答。不要为了检查重新询问已确定的事项或制造新问题。

讨论中处理完用户回答、补查或局部请求后，准备提问、进入计划或结束回复前，以及执行前，必须调用 `scripts/workflow_control.py next` 并执行返回的下一动作；脚本只读标准输入或指定的 JSON 状态，不创建、覆盖或更新任务记录。例如 `python3 -B "<skill目录>/scripts/workflow_control.py" next --state -` 从标准输入读取；`check` 只检查结构。脚本未运行或失败不等于检查通过；不可用时说明限制，并按主控协议继续。

状态包含 `task_id`、`phase`、`status`、`next_action`、`decisions`、`plan`、`coverage_checked`、`plan_requested` 和 `gates`；执行前还须填写 `goals`。决定项记录稳定 `id`、主题 `subject`、`status`、实际决定 `value` 和 `source`；待定项不需要 `value`。计划与目标各自的 `presented` 和 `evidence` 来自对话中实际可见的内容，同轮展示可引用同一消息；局部调整时分别保留原展示与增量展示的可追溯引用，未展示完整原文不能把增量当作首次完整展示；不由脚本自行判断消息是否送达。`goals` 可在展示前省略，进入执行时须为 `{"presented":true,"evidence":"实际目标展示来源"}`；计划请求和授权分别保留来源。`plan_requested` 表示当前须交付计划：用户请求计划，或用户要求跳过计划并执行且讨论已闭合时按主控进入计划阶段；后一种情况的来源如实指向跳过请求，不把它写成用户主动要求计划或内容确认。讨论尚未闭合时先处理必要事项。`plan_required:false` 仅用于无需进入正式计划阶段的收口（如已有结果满足任务），不能用于跳过计划。`plan_request_source` 使用能唯一标识该次请求的实际消息引用。同一请求的草案已交付时，`plan.draft_for_request` 填完全相同的请求引用；若有依据确认旧草案不对应当前请求，`plan.draft_not_for_request` 填当前请求引用，即使旧请求的来源无法恢复也不编造。新草案实际交付后同步更新草案证据和 `draft_for_request`，清除对应的 `draft_not_for_request`；不能提前记录交付。不同引用可能只是不同写法，未确认关系时脚本返回 `verify_plan_request`，先核对对话再更新，不推定已送达或重复提问；确实无法判断时保留未知，不假称核实。用户只回答一部分时，只更新实际覆盖的决定。填写状态前先查对话和材料，无法恢复的事实标为未知，不猜测。

以下是结构示意，必须按实际对话填写，不把示例当作已有决定：

```json
{"task_id":"当前任务","phase":"analysis","status":"continue","next_action":"分析当前请求","decisions":[],"plan":{"presented":false},"coverage_checked":false,"plan_requested":false,"gates":{"plan":null,"goals":null,"execution":null}}
```

插入请求使用 `interruptions` 数组，原阶段和状态留在原字段。处理前以原状态调用 `next`，临时事项填 `id`、`request`、用户消息 `source`、`status:continue` 和 `next_action`；等待脚本返回，将 `resume_point` 原样放回该项并保留后，再调用临时事项的工具，不得并行。它只包含原环节、状态、下一动作及等待依据，不复制完整计划和目标；原待答问题不能因插问被记成已答。嵌套插入按顺序追加，不能覆盖未完成事项。

临时事项受阻时填 `blocked` 和 `wait_reason`，脚本返回 `wait_interruption`；等待用户时另填已展示问题的 `wait_evidence`。用户明确取消则记 `cancelled` 与用户来源，用户要求继续且权限允许时记 `continue`；按实际意思判断，不匹配固定关键词。完成或取消须填实际结果或取消依据 `result_evidence`，连同已保存的 `resume_point` 再调用 `next`；脚本返回 `reconcile_interruption` 和恢复点。先核对结果、最新要求及原状态，在正文交付临时结果或说明取消，再接回原事项；新信息影响原决定时只更新受影响部分，不预记正文已交付。恢复点缺失时从可用对话或摘要补查，不猜测。

原任务明确暂停时，仅在用户另行要求临时事项且未暂停全部工作时，才设 `allow_while_paused:true` 及其用户消息 `allow_while_paused_source`；接回后仍保持暂停。临时事项被用户暂停后恢复须提供 `resume_source`。原状态存在结构或执行门槛错误时，`original_state_errors` 须在恢复原任务前处理，不妨碍独立且获准的临时请求。恢复不必传两份完整状态；已有 `previous` 时仍可用于原有的跨轮检查。脚本只返回结果，不自行写记录或授予权限。

如果有正在运行或结果未知的操作，可用 `operations` 保存其 `id`、实际 `reference`、`status`、`side_effect` 和 `blocks_next`。`blocks_next`、`blocks_completion` 按依赖判断，与是否有副作用无关；`side_effect` 用于判断结果未知时能否安全重试。同一操作不应换标识重复记录；不阻止下一步不自动等于可以宣告整项完成。

脚本返回下一动作供主控执行：主任务执行受阻但计划和目标可在授权内展示时，填 `independent_action` 为一起展示计划和目标；脚本返回 `continue_local` 并保留原阻塞原因。若该字段遗漏，但计划已展示、目标未展示且本轮不限于局部，脚本仍要求核对当前范围及确认依据，允许时一起展示计划和目标，不自行认定已授权。临时事项受阻仍保持等待。仍有影响方案的待决项时调查或讨论；用户要求计划且讨论闭合时列出计划，未闭合时可给标明缺口的草案；其他没有计划请求的情况按主控请求结束讨论。讨论闭合并进入正式计划阶段时同轮展示计划与目标；用户明确限定本轮只能展示其中一项时按主控等待调整限定。旧草案的待核实状态不能挡住已确认的正式计划。计划展示不是确认或执行授权。执行中准备继续实际操作时，覆盖尚未核对或仍有影响方案的待决项，脚本要求先修正状态并处理缺口；已完成的本轮局部动作可按限定收口。用户暂停或明确限制本轮范围时优先遵从；未知副作用先核实原操作，不盲目重试。

有上一状态且涉及计划请求撤回、暂停恢复或决定变化时，可以传入 `{"previous":上一状态,"state":当前状态}` 检查明确变化，输出 `scope: structure_and_changes`；未提供上一状态时无法检查跨轮变化。若本次计划已在上一状态交付而本轮才清除请求，记录 `plan_request_delivery_source` 指向本次实际交付；旧计划不能冒充新请求的交付。脚本输出的 `scope: structure_only` 表示只检查结构；它不验证来源的真实性、决定是否被正确理解、问题覆盖是否完整或消息是否实际送达，也不能强迫模型调用。不可访问消息记录文件不妨碍通过可用对话判断下一步；证据不可核实就保留未知，不把普通文件冒充宿主回执。原有摘要的写入、并发和恢复仍由[记录模块](state-recovery.md)处理，本检查器不替换摘要文件。
