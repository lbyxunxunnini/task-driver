# 业务场景最佳实践

本文件帮助模型和用户判断不同任务应重点讨论什么。场景建议不能代替用户决定，完整流程仍以根目录 `SKILL.md` 为准。

## 调研与讨论方法

开始需求调研前必读本节。先确定当前任务类型，不向用户增加分类问题。用户当前只询问环境限制或调研能否继续，且相关事实已明确时，必须按以下短格式答复后结束本轮，不加子项；禁止展开后续需求清单、技术选型或确认继续的选项：

```text
当前可做：{本轮在现有能力内能完成的事，一句话}
证据缺口：{不能完成或声称的事及原因，一句话}
下一步：{恢复所需条件或当前可行路径，一句话}
```

### 按任务类型调研

- 已有项目改造：必须理解项目定位、结构、相关业务与实现、依赖和改动影响，禁止只看拟修改位置就下结论。
- 已有项目新增诉求：必须先理解项目及能力缺口，再联网搜索成熟方案，重点调查 GitHub 实现并比较适配性、限制和代价。
- 许愿式需求、空项目：必须先用自身知识分析场景和可行路径，再联网充分搜索成熟方案，重点调查 GitHub 实现；不得因为没有代码而直接问需求表单。

已有项目先读适用规则和可靠摘要，核对目录与入口，再沿业务流程、实现、依赖及已有验证核实用户问题是否成立，追踪实际缺口、改动影响和更简单的处理；摘要与源码冲突时以核实后的事实为准。新增诉求须先识别可复用能力和缺口，再比较真实实现、文档和维护记录及接入方式；空项目须比较成熟方案的能力、机制、使用条件、代价与适配性。

搜索围绕当前问题，不设固定仓库数。阅读原始文档和实际实现，不能以星数或搜索摘要替代成熟度与适配性判断；不复制未经审查的代码。非软件产物没有适用仓库时，核实并说明 GitHub 适用性，使用领域原始资料，不虚构仓库方案。

形成判断前必须能说明：实际问题、可行方向、依据、主要限制和用户未决事项。调研结果不是用户决定；信息不足先补调查，不把查资料转给用户。

每轮说明当前发现与判断，给有依据的建议，只请用户决定未决关键取舍。暂时没有必要问题时继续分析；当前项闭合后转下一未闭合项。用户回答后吸收决定，不重复问已明确内容。

同一处反复讨论而无进展时，查明是缺证据、解释不清还是真实分歧，分别补调查、给例子、说明冲突及影响。禁止换措辞追问或增加无关字段。关键事项闭合才可按主协议请求结束讨论，不按固定轮数收口。

### 完整测试用例的计划方法

先核实实际业务入口、规则、状态变化和已有测试；据此确定覆盖范围，分析适用的正常、异常、边界及状态转换场景。计划必须说明如何写成带前置条件、操作、数据和预期结果的用例，并与业务范围对应核对遗漏。平台差异根据实际实现标注，不把共用流程重复写两遍；自动化按已确认需求和实际可操作性确定，不默许真实付费操作。

以上是实施方法，不自动要求额外报告、矩阵或文档；最终交付按用户确认范围组织。最终目标是用例能指导执行并覆盖约定业务，不是“分析完成、文档写完、检查通过”。

## 执行并发判断与分派

本节约束参与实现的执行子代理，不改变第七步独立审查的启停、角色和要求。

- 任务开始时必须先分析执行依赖和改动影响范围，再决定执行方式；任务大、文件多或工具支持子代理，均不能单独作为并发依据。
- 以下条件全部满足时，必须拆分并发：每个子任务的目标、输入、交付物、修改范围和完成标准明确；能够独立开始，不依赖其他子任务尚未产出的结果；改动不改变其他子任务依赖的接口、数据结构、配置或业务行为；不同时修改同一内容，不争用会相互干扰的运行资源；执行并发已在用户授权范围内。任一条件不满足或无法确认满足时，必须由主线程串行执行。修改不同文件不能代替上述判断。
- 后一步依赖前一步结果的递进任务，或无法确认相互独立的任务，必须由主线程串行执行；禁止假定前序结果或让多个代理各自决定公共约定来制造并发条件。用户明确关闭子代理时，禁止启用执行子代理。
- 在现有计划的实施方案中简述执行方式和依据；并发时列出各子任务的目标与修改边界，随原有计划及执行确认获得授权，不增加表单或确认轮次。执行子任务仅用于内部分派，不增加最终验收目标，也不得作为额外的宿主验收任务创建。
- 主线程负责分派和整合；执行子代理只在获派范围内实现，返回实际改动与验证证据。执行中发现依赖或交叉影响时，必须停止受影响的并发工作、保留已有结果，由主线程接回处理。
- 子任务完成不等于整体完成；整合后仍按原有最终验收目标、自检和已开启的独立审查要求判断结果。

## 低风险 Bug 修复

适用情况：问题范围明确、改动可逆、不涉及外部权限或生产操作。

重点讨论：

- 用户可见的错误表现和正确表现。
- 只修当前问题还是覆盖相邻同类问题。
- 哪些现有行为必须保持不变。

计划重点：说明根因方向、核心修复机制和影响边界，不按文件拆成施工清单。

最终验收目标：错误不再出现，相关正常路径保持原行为。

Agent 内部验证：复现问题、运行相关测试、检查回归路径和差异范围。

用户验收：通常不需要；只有 Agent 无法访问真实界面或设备时才请求。

停止或拆分条件：发现根因涉及独立模块、权限或另一个业务目标时，返回讨论并确认是否拆分。

## 新功能或新模块建设

适用情况：需要新增用户能力、接口、模块或完整产物。

重点讨论：

- 为什么需要该能力，最终使用者是谁。
- 正常路径、失败路径和明确非目标。
- 核心接口、数据、交互和兼容取舍。

计划重点：展示总体实施机制、模块边界、数据或交互流和必要集成点。

最终验收目标：用户能够完成新能力对应的完整结果；失败时有明确行为。

Agent 内部验证：端到端小案例、单元或集成测试、错误路径和兼容检查。

用户验收：涉及主观体验、真实业务数据或私有环境时需要。

停止或拆分条件：一个请求包含多个可独立交付能力，或不同能力需要独立发布和回滚时拆分。

## 跨模块重构

适用情况：目标是改善结构、迁移接口或替换内部机制，同时保持用户行为或明确改变部分行为。

重点讨论：

- 重构的业务原因和必须保持的外部行为。
- 允许改变与禁止改变的接口、数据和兼容边界。
- 迁移顺序、回滚路径和完成分母。

计划重点：说明新旧结构、迁移路径、兼容策略和每个阶段怎样保持系统可用。

最终验收目标：确认范围内完成迁移，外部行为符合约定，没有遗漏旧入口或静默降级。

Agent 内部验证：范围清单、调用链检查、迁移前后行为对比、回滚和集成测试。

用户验收：涉及真实生产流量、业务报表或外部消费者时需要。

停止或拆分条件：不同模块可独立迁移、需要不同负责人或回滚周期时，按迁移批次拆分。

## 生产配置、外部接口或费用任务

适用情况：涉及生产环境、真实 API、费用、发布、权限或不可逆操作。

重点讨论：

- 明确授权范围、费用上限和可操作环境。
- 成功、失败、降级和回滚路径。
- 凭据来源、敏感信息边界和外部服务限制。

计划重点：说明调用或发布机制、风险控制、停止条件和回滚方式。

最终验收目标：授权范围内的真实结果达成；失败时没有越权、超额费用或不可恢复状态。

Agent 内部验证：尽可能先用只读、模拟、隔离或最小真实调用验证。

用户验收：Agent 无法访问真实账号、生产结果或外部控制台时必须请求。

停止或拆分条件：缺少授权、费用确认、凭据或回滚能力时立即停止，不消耗修复次数。

## UI、设备体验或主观质量任务

适用情况：结果依赖视觉效果、触控体验、声音、真实设备表现或人的主观判断。

重点讨论：

- 目标设备、环境和主要用户路径。
- 用户认为通过与不通过的具体表现。
- Agent 可以自动验证的部分和必须人工验收的部分。

计划重点：说明实现方法、目标环境、可自动检查内容和用户验收安排。

最终验收目标：目标环境中的实际体验符合用户确认的表现，没有已知瑕疵。

Agent 内部验证：构建、静态检查、自动化测试、截图或可访问环境中的行为验证。

用户验收：给出具体设备、操作步骤、预期结果、通过条件和反馈要求；反馈前不能标记达标。

停止或拆分条件：不同设备或体验路径具有独立结果和独立修复方式时，可按环境或用户路径拆分并说明原因。
