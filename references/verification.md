# 验证取证

输入：当前有效目标及通过条件、当前产物和环境权限。输出：实际操作、观察结果、证据来源、覆盖和未核实部分。禁止因缺少证据判定实际失败或通过。验证结果必须交给[审查模块](review.md)判断证据充分性，由主控决定完成。

## 验证前限定范围

首次验证和追加取证前，必须在当前上下文按[统一范围判断](review.md#审查发现的范围判断)明确取证范围及要证明的内容。定向检查能覆盖时必须采用；用户或适用项目规则明确要求全量检查时，必须按要求执行。

共用检查混有范围外失败时，必须逐项核对输出是否覆盖必要证据，有缺口时必须定向补证。整体通过本身是既定条件时，必须按该条件验收。

排定取证顺序时，必须分别判断本项是否影响下一次验收和最终完成。用户或适用规则明确要求先做，或有具体依据表明缺少本项会使下一项无法进行、证据失真或产生实际风险时，必须先解决依赖；否则必须优先开展已获准且能独立取得有效证据的验收，完成前必须补齐仍必要的检查。禁止以历史可选检查或缺乏具体依据的疑点阻塞。新计划必须按实际依赖排序，已确认顺序必须按[计划修订规则](planning.md#讨论并确认计划)处理。

例如，缺少当前构建或正确的设备配置会让模拟器验收无效，先补齐。若当前产物和环境已就绪，另一项必要回归与本次设备观察互不依赖，可以先跑模拟器，再补回归。

## 选择能证明目标的方法

| 目标性质 | 合适的证据 | 单独不足以证明目标的内容 |
|---|---|---|
| 指定文本或配置修改 | 当前文件读取、前后差异、范围保持检查 | 声称“已改”、准备写入的文本 |
| 功能在约定场景可用 | 实际输入、执行路径、可观察输出及必要异常/回归 | 文件存在、编译成功、计划完成 |
| 模型交互行为 | 使用固定协议快照的真实多轮对话、工具事件、实际产物及状态变化 | 规则关键词存在、模型自评、问题数量 |
| 提问语义复核 | 原始对话、待决项与决定来源、独立上下文或主模型结构化复核记录 | 仅存在 `semantic_review` 字段、仅脚本通过、仅复核者自报 |
| 外部环境或设备结果 | 授权环境中的真实操作、日志或可核实反馈 | 离线模拟替代真实部署或设备结论 |
| 创作或主观体验 | 实际产物、自身可做的内容与显示检查、必要用户反馈 | 提示词存在、文件可解码替代审美通过 |

静态检查可以直接证明文本类目标，也可辅助功能验证。`semantic_review` 提供复核契约与证据入口，禁止仅凭该字段声称已做独立复核，尤其禁止把 `main` 自检写成独立复核。模拟测试必须说明覆盖条件，禁止据模拟成功声称真实业务成功。无法验收的环境必须标明缺口，禁止自行降低原通过条件。

## 执行验证

运行验证前，必须把目标转成可观察的输入、动作和预期结果。必须按用户要求和实际风险选择必要负例与边界，禁止随意新增目标。必须记录真实输出，禁止只记退出码。必须区分执行失败、条件不足和结果不满足。

验证持续较久或用户询问进度时，必须说明现有证据和仍缺的取证、修复、步骤、独立复核、交付或用户验收。用户指定的额外验证必须单独说明状态；内部进度锚点必须按记录模块处理。

当前条件无法验证目标时，必须先判断能否在授权内通过临时预览、测试输入、基准对比等方式取证；能做时必须主动验证并说明覆盖范围。

通过条件的实际证据必须按 `goals.included` 的 id 写入 `goals.evidence_map`。每条记录必须用 `kind` 区分工具结果（`tool`）、产物实际读回（`artifact`）和用户反馈（`user`），用 `source` 指向可回查的输出或反馈，用 `subject` 标明实际检查的产物、版本或运行，用 `observed` 写明实际观察及所覆盖的条件。用户反馈的证明范围必须限于用户明确确认的结果。失败、无法判断和未覆盖的部分，必须记入现有验证结果，并保留相应目标未完成。

完成前必须逐项回查证据来源。确定性检查必须核对实际输出和断言是否命中目标；界面或外部行为必须核对实际触发和观察。必要条件缺证据时必须定向补查。禁止使用旧产物、失效环境或来源不可核对的引用判定当前结果通过，禁止把模型自述、通用成功提示或未来计划计作证据，禁止单独验收 `goals.excluded`。

用户额外指定的验证与现有 included 无对应关系时，必须按实际结果在现有任务记录或交付报告中单独说明，禁止挂到无关目标或自动新增验收目标。涉及明确排除项时，必须先按用户最新要求处理范围变更。

送审时必须逐项说明必要结果的验证方式、实际观察及未覆盖部分。多种证据共同支持一项目标时，必须分别说明各自的证明范围，禁止以一种证据扩写另一环境的结论。

用户明确要求结束时，必须按[目标拆分与证据映射](goals.md#目标拆分与证据映射)记录 `completion_basis:user_requested`、用户来源及 `unverified_goals`，正文必须分别报告已完成和仍未验证的结果，禁止把未验证项写成通过。

必须核对证据对应当前产物及实际环境。产物变化时必须重验受影响路径，禁止将旧快照结果拼成新版本通过。未受影响且仍有效的证据必须按原范围保留，可继续复用。禁止借复用省略尚未验证的必要场景。多轮行为测试必须保存任务输入、协议快照、逐轮回答、工具动作和实际变化，判据必须留在测试侧，禁止提示被测模型如何通过。

验证完整讨论流程时，必须覆盖按[主控入口](../SKILL.md#接到任务后的第一步)发生的真实收口问答与正式计划、验收目标的同轮展示，并核对必要事项是否覆盖、待决项如何处理、委托边界是否得到遵守，以及是否出现多余追问。未覆盖完整流程时必须说明，禁止声称全流程通过。验证恢复能力时，必须在获准的隔离进程或可控服务中观察运行中断连、操作成功但返回丢失、部分失败后的续接，并核对运行标识、实际副作用和重复次数。模拟材料、真实隔离运行和生产现场的结果必须分别报告。

必须按[目标与验证模板](templates.md#目标与验证模板)记录验证结论。发现缺口时，必须交回主控决定调查、讨论、修复或必要用户验收。禁止把验证作为额外收费、发布或修改生产系统的授权。

## 用户验收补位

用户明确要求亲自验收，或已确认结果仍涉及 Agent 无法可靠验证的主观体验、私有账号、真实设备或外部环境要求时，必须先完成自身可做的检查，再请求用户补足对应结果的反馈。禁止因任务简单或部分检查通过而跳过必要验收。

当前证据已覆盖全部已确认结果且用户未要求亲自验收时，禁止额外请求确认。例如指定文字修改经当前文件、差异和范围保持检查即可证明结果。必须按用户要求和证据覆盖判断是否需要用户验收，禁止凭“简单任务”或“Bug 修复”一概豁免，或用执行授权替代对实际结果的验收。

需要用户验收时，必须先读取或复用[用户验收通知格式](templates.md#用户验收通知格式)，提供编号操作、预期结果、通过条件和所需反馈证据。禁止只说“请自行检查”。

等待必要反馈时必须保持未完成，反馈的效力必须限于实际验收范围。反馈中发现的问题必须按[统一范围判断](review.md#审查发现的范围判断)处理，即使用户已认可某项交付。验收未通过时必须按[主控](../SKILL.md#展示与确认策略)承接。用户无法完成必要验收且无可靠替代证据时，必须标为受阻。

涉及生产、费用、发布、覆盖、删除或安全权限时，必须核对目标、授权动作和可恢复路径。可用授权内工具和证据核实时，必须先自行验证；仍无法可靠核实的结果必须请求必要用户验收。禁止仅因高风险就重复确认所有事项。

## 候选与测试材料隔离

调用被测模型前必须冻结协议和实际任务需要的原始材料。评测判据、角色回答、历史失败、当前报告与审查结论必须留在控制端。采用源码子集时，必须记录白名单和哈希，并明确未提供的材料不能据此判为原项目缺失。正式协议的示例属于产品内容，禁止把它当隐藏判据。每个样本必须先验证实际基线，基线失败的轮次必须记为失败或无效覆盖，禁止挪作目标故障恢复成功。

必须根据实际工具事件和产物核对行为顺序。运行中状态必须记录观测时间和任务完成时间，并区分持续观察、合理宿主限制和无依据等待用户。必须如实记录测试宿主、实际模型和隔离能力，禁止用命令行产品名冒充模型名，或把仅以提示约束的工作目录写成强制沙箱。
