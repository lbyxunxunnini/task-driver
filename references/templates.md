# 模板参考

SKILL.md 各环节引用的展示模板，集中维护于此。

## 轻量计划摘要模板

保存和恢复方法以[记录与恢复](state-recovery.md)为准；只填当前需要的内容，未知保留未知。文件名沿用 `.task-driver/{任务标题}-{时间戳}-计划摘要.md`，已有记录复用。

```markdown
# {任务标题} 计划摘要

## 当前状态
- 最终范围 / 当前环节 / 推进状态：
- 当前允许动作及来源（引用下表，不重复抄写）：
- 当前事项及未答部分 / 下一动作 / 所缺条件：
- 临时事项（如有）：原阶段、原状态与下一动作 / 临时请求、来源与状态 / 结果及恢复核对：
- 四项引证：计划与目标展示 / 计划确认 / 目标确认 / 执行授权（展示和确认分别对应实际消息；同轮展示可共用引用）：
- 执行入口凭据：分析/讨论闭合、编号步骤、allowed_paths/allowed_actions、实际宿主 ID 与执行中回执，或经用户确认的有效降级依据；`execution_receipt`：
- 目标跟踪：`goal_tracking_mode` / `goal_tracking_source` / `goal_tracking_confirmation_source`；`goal_tracking_host_id` + `goal_tracking_host_receipt` + `goal_tracking_host_kind` + `goal_tracking_host_readback`（实际返回的 ID 与正文），或 `goals.local_goal_id` + 降级原因、能力证据：
- 暂停或等待原因 / 恢复条件 / 恢复后第一步：

## 事实、约束与决定
事实和规则记来源及适用范围，模型建议与待证推断单列；用户决定只在决策表记录一次。只有需要跨表引用或回取的条目才编号，规则见[记录与恢复](state-recovery.md#引用与展开)。编号和引用列不需要时留空；证据、操作与复核通常内联在对应目标、操作和次数单元格中，需要单独引用时再使用 `E{n}`、`O{n}`、`R{n}`，并记录摘要与位置。

| 编号（如 F1） | 事实/规则/建议 | 来源及性质 | 适用范围、有效性或待核实处 | 引用 |
|---|---|---|---|---|

每个独立问题一行，保留原文或足以辨认的完整内容；一个提问包含需分别回答的独立问题时分行，方案或计划的一次整体确认保留一行及实际确认范围；同一事项的多个问题关联但不合并为同一条目，分行不新增用户追问。有效事实、规则及不对应提问的决定也单独记录。只更新受影响条目。

| 编号（如 D1） | 事项 / 问题及送达依据 | 状态（拟提/待答/已答/委托/排除） | 答案或决定、用户原话或消息来源及实际确认或委托的内容与范围 | 未覆盖部分 / 下一动作 | 引用 |
|---|---|---|---|---|---|

- 覆盖、决定、未知处理核对结果；当前问题引用的决策项：

## 有效计划与步骤
- [ ] P{n} {事项} — pending / in_progress / blocked；实施方法、依赖与所需条件；位置与引用：
- [x] P{n} {完成事项} — done；实际结果及证据引用（E{n}）

`plan.steps` 与记录中的 P 项一一对应；同一时间最多一项 `in_progress`，前项未完成时后项不能标为 done。
进入执行时，`execution_scope.allowed_actions` 必须精确包含上面每个步骤的 `action`；只读等待动作另用 `read_only_scope` 记录。
用户要求结束时，未完成步骤逐项写入 `unverified_plan_steps`，不要用目标证据替代步骤状态。

## 目标与证据
| 编号（如 G1） | 目标原文及来源 | 通过条件 | 证据及产物版本 | 未核实部分与状态 | 宿主ID/local_goal_id | 引用 |
|---|---|---|---|---|---|---|

- `goal_scope_baseline`：当前 included/excluded 的已确认范围快照；隐藏目标时保留，不随 `presented:false` 删除。无 Goal 模式时使用稳定的 `local_goal_id`，不要伪造宿主 ID。

## 操作与交接
- 重要动作意图、授权引用、可查询操作标识、实际结果或结果未知、核查入口：
- 本轮改变/失效内容与仍有效内容（引用原条目，不另存副本）：
- 已用修复/独立复核次数、上限：
- 进度锚点：`A{n}` 判定、依据摘要、建议、是否执行及未执行原因：
- 必要交付消息或渠道 / 宿主同步结果（尚未发生则待办）：
```

## 计划草案展示模板

正式计划必须展示“已确认”“实施方案”和编号“执行步骤”；复杂任务再按主协议补充后列的可选内容，不为填模板新增问题。

```markdown
# 计划草案

任务目标：{本次任务最终要达成什么}

## 1. {计划事项}

### 已确认

- {用户确认的决定、适用规则及来源；明确委托只写委托对象和范围}

### 实施方案

{具体完成方法、作用边界和关键约束；委托内由模型作出的决定及委托来源；“完整”等要求如何覆盖并核对遗漏，不只写分析/编写/检查}

### 执行步骤

1. S1 [pending] {第一步动作及完成条件}
2. S2 [pending] {第二步动作及完成条件}
```

可选内容仍归对应计划事项：

- 预期变化：当前表现及实施后的用户或系统表现。
- 涉及位置：主要文件、模块、流程或产物，以及准备调整什么。
- 内部验证：使用的行为回放、测试或检查。

## 内容展示与执行选择模板

满足[主控合并展示条件](../SKILL.md#展示与确认策略)时使用以下内容模板；末尾仅询问尚缺的确认，已有确认、委托或豁免按主控直接沿用。目标按实际最终结果组织，不按实施步骤逐项生成。

```text
计划：{已确认内容、具体实施方法}

纳入验收（included）：
- G1 [{changed|associated}] {对应需求的可验证最终结果}；来源：{需求或确认}

明确排除（excluded）：
- E1 {用户明确不纳入本次验收的内容}；来源：{用户消息}

{仅在尚缺内容确认时，请用户确认对应内容；否则按主控承接，不重复询问}
```

[主控](../SKILL.md#展示与确认策略)判断既缺少子代理设置也没有明确委托时，使用以下模板；用户已有明确设置或委托时保留原设置/由模型决定，只补齐缺失的执行范围授权，不重复提供子代理选择。

```text
计划与目标的确认依据已齐备，请选择执行范围与子代理设置：
1. 执行，开启子代理：{本任务拟分工与独立复核安排、资源代价；推荐时给理由}
2. 执行，不开启子代理：主模型执行、验证和审查修复。{推荐时给理由}
3. 不执行，继续讨论：暂不执行，调整计划或目标。
```

以上执行选择必须标注一个推荐项，不照抄占位符。分派、独立复核与长任务检查按[子代理管理](subagents.md)和主控执行；呈现方式按主控回复提交门禁，不在模板重复定义流程。

## 独立审查交接模板

仅已开启独立审查时使用，首审与复审均在独立上下文中交接。以下内容填入真实目标、权限、证据和可访问的协议位置后直接作为审查任务，不把模板占位符发给子代理。

```text
当前有效目标：{用户当前确认的验收目标原文；已被新范围取代的旧目标标为 `superseded`，不附达成状态}
范围与限制：{当前审查对象、授权内的核实操作、用户限制，以及影响判断的已确认业务口径、验收边界和来源}。审查前先读取 {当前 references/review.md 的可访问位置} 的“独立复核要求”，按其中的输入检查和输出要求审查。
当前产物与客观证据：{当前版本及核实各目标所需的文件、原始输出；流程事实对应实际消息记录}
本次变更（仅复审）：{本次客观差异及待核实影响；首审省略此字段}
```

若子代理无法读取该位置，将上述读取指令替换为审查模块输入检查和输出要求的原文，仍放在“范围与限制”中；不要求用户安装工具。不得交付执行者自评或前次审查结论。

## 进度锚点交接模板

仅长任务达到[进度锚点条件](state-recovery.md#进度锚点)且已获授权时使用。只读，不写文件，不判断最终完成。

```text
目标锚：{当前有效目标原文与通过条件，旧目标标为 `superseded`，不附达成状态}
路线锚：{当前计划项原文；最近 3 条阶段结果，每条一句话并附编号}
动作锚：{最近若干次实际动作及结果，不含完整日志}
边界锚：{当前环节、允许动作、已用修复/复核/锚点次数、用户明确限制}
请只输出：判定（在轨/偏离/无法判断）、依据（对应上述哪一条）、建议（继续/回到某项/补证据/交回讨论）、限制。
```

## 统一异常通知骨架

所有异常通知使用统一骨架：当前结果：{做到什么程度}、原因：{为什么没有继续}、已完成：{已完成内容}、下一步：{修复方式或用户操作}，并根据异常类型补充必要内容。

补充规则：

- 未达标：说明当前是第几次修复，以及本轮准备改变什么。可修复问题回复用户时只说明：哪条没达标、失败原因、本轮改变了什么、当前是第几次修复。
- 需要用户验收：提供编号步骤、预期结果、通过条件和反馈要求，必须同时遵守下节[用户验收通知格式](#用户验收通知格式)。
- 需要用户授权或决定：明确说明用户需要授权或选择的唯一当前事项。
- 受阻：说明已经尝试过什么、为什么没有替代路径，以及当前目标和文件状态。
- 通知只展示用户做决定需要的信息，不粘贴长日志或内部状态转储。

是否继续、等待或完成由[主控](../SKILL.md#阶段转换)判断，本模板只呈现异常事实与下一动作。只有当前任务确实需要用户决定才能继续时，“下一步”才给可直接选择的方案、各项影响、一个推荐项及理由；已有授权范围内的修复直接处理。

```markdown
## {未达标 / 需要用户验收 / 需要用户授权或决定 / 受阻}

当前结果：{当前做到什么程度}

原因：{为什么没有继续或没有达标}

已完成：
- {已经完成的内容}

下一步：{agent 将怎样修复，或用户需要完成什么}
```

## 用户验收通知格式

需要用户补充操作或证据时的通知要求：

- 必须明确通知“需要用户验收”，不能把验收请求隐藏在残余风险或普通建议里。
- 验收步骤必须针对当前目标编写，能够直接操作，并包含预期结果和通过条件；步骤、条件和反馈只保留判断该目标达成所必需的内容，不得新增模型自造标准、无关操作或信息要求。
- 必须说明需要用户验收的具体原因（证据缺口或用户明确要求亲自验收），以及用户需要反馈什么结果或证据。

完成判定、反馈不通过及无法验收时的处理，分别见[用户验收补位](verification.md#用户验收补位)、[异常分类](review.md#异常分类)与[主控完成门槛](../SKILL.md#完成门槛)。

```markdown
## 需要用户验收

当前结果：{agent 已完成的检查和当前产物状态}

原因：{尚缺的可靠证据，或用户明确要求亲自验收的内容}

已完成：
- {已经完成的实现和内部验证}

验收步骤：
1. {验证当前有效目标所必需的操作及预期结果；被用户新范围取代的旧目标标为 `superseded`，按实际需要续编号}

通过条件：
- {仅核对当前有效目标的明确结果，不新增条件}

请反馈：
- {判断当前有效目标达成所必需的通过/不通过结果或证据；旧目标标为 `superseded`}

下一步：{反馈用于证明哪个条件；按主控转换承接，不预写完成}
```

## 目标与验证模板

目标定义见[目标模块](goals.md)，取证方法见[验证模块](verification.md)。目标阶段只用下面的“目标草案”部分；验证后用“验证结果”部分。只记录真实观察，不将预期结果填入实际结果。

### 目标草案

```text
included（纳入验收）：
- G1 [{changed|associated}] {用户需要且可观察的结果}；来源：{需求或确认}
- G2 ...

excluded（明确排除）：
- E1 {不纳入本次验收的能力或依赖}；来源：{用户原话或消息}

evidence_map（完成前补齐）：
- G1 → {环境、输入、动作、实际观察结果及证据位置}
- G2 → ...

goal_scope_baseline：{当前 included/excluded 的已确认范围快照}

completion_basis：{evidence | user_requested}
completion_request_source：{用户明确要求结束时填写}
completion_report：{verified_goal_ids: [...], unverified_goal_ids: [...]}
unverified_goals：
- {G2｜仍未验证的内容｜原因｜实际影响；没有则留空}
```

### 验证结果

```text
对应目标：{当前有效目标原文或编号；旧目标标为 `superseded`}
实际结果：{观察到什么；未执行写未执行}
证据：{可访问来源及对应产物版本}
覆盖与限制：{证明了什么、未核实什么}
完成口径：{evidence｜user_requested；user_requested 填写用户来源}
未验证项：{逐项写缺少什么及原因；没有则写无}
结论：{未验证 / 达成 / 未达成 / 受阻；证据尚未取得但可取得记未验证，必要证据无法取得且无替代路径才记受阻}
```
