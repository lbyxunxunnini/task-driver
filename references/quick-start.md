# 快速开始

先用 [30 秒选择器](../SKILL.md#30-秒选择器)判断是否需要任务驱动；简单问答、安全单命令和明确要求直接处理的低风险单文件小改动可直接处理。

## 按需阅读

- 不清楚流程原因、状态、权限或重试规则：查看 [常见问题](faq.md)。
- 需要判断某类任务怎样讨论和验收：查看 [业务场景最佳实践](scenarios.md)。
- 需要完整协议：查看根目录 [SKILL.md](../SKILL.md)。

## 固定链路

```text
仔细询问并逐项讨论
-> 输出计划
-> 一并展示验收目标草案（能一起讲清楚且无新关键取舍时）
-> 确认计划、验收目标与执行授权（有关键取舍时只讨论当前问题）
-> 创建目标并执行
-> 未达标或无法确认达标时先分类
-> 可修复问题打回修复，最多 3 次；其他异常进入对应路径
```

## 每一步怎么说

### 逐项讨论

先调查必要事实，判断问题与方案是否成立，再给出有依据的建议；只询问分析后仍需用户决定的取舍，一次只讨论一个问题，不强制每轮提问。

```text
用户提出“退出前加确认弹窗”时，不先追问弹窗文案。
先检查是否存在未保存内容、当前保存机制及退出后的实际后果。
如果确认只有未保存修改会丢失，建议仅在该情况下提示，避免每次退出都打扰用户。
再说明仍需用户决定的取舍及理由；若没有必要取舍，先报告判断，不制造问题。
```

用户的办法存在缺陷时明确指出，证据不足时说明不确定性。不要把事实调查转交用户，也不要顺带展开其他讨论事项。

### 结束讨论

模型判断关键问题已经闭合后，只能提供选择，不能直接输出计划。

```text
当前关键问题已经讨论充分。

请选择：
1. 结束讨论并生成计划。
2. 继续讨论。
```

### 输出计划

顶层计划事项对应已确认的需求或问题。每项必须包含“已确认”和“实施方案”。

```markdown
# 计划草案

任务目标：修复登录按钮错位。

## 1. 修复按钮位置

### 已确认
- 只修登录按钮，不统一其他按钮样式。

### 实施方案
调整按钮所在布局的对齐约束，保留现有视觉样式和其他按钮行为。
```

复杂任务可以增加“预期变化、涉及位置、内部验证”。不要把文件、测试和版本更新拆成新的顶层事项。

### 一并展示与确认

计划与验收目标能一起讲清楚且无新关键取舍时，倾向一起展示。最终验收目标使用简短编号列表，只展示必要终极结果，例如：

```text
1. 桌面宽度下登录按钮保持在预期位置，其他按钮样式不变。
2. 移动端窄屏下按钮保持在表单容器内，不发生横向溢出。
```

明确询问是否按以上计划、最终验收目标及授权范围开始执行。用户确认整体执行请求后，直接执行，不追加同内容的确认。独立审查开关仍按主协议在最终确认前询问。

用户只看计划或暂不执行时不执行。有新关键取舍或用户要求拆开时，只讨论当前问题，保留已确认内容；口径闭合后汇总受影响内容，不重启流程。实际运行或等待验证不自动增加执行前的确认轮次。

不设置固定条数。合并或拆分时说明对应的原始事项和原因。测试、脚本、文档和版本默认留作内部证据。

### 创建目标并执行

用户确认最终验收目标后，原样创建目标或维护轻量目标，再连续执行。目标工具的 schema 未加载时先通过 `ToolSearch` 精确加载；宿主任务创建后保存 ID，开始执行时同步为执行中。未开启独立审查时，自检达标后同步完成；已开启时，等待独立审查全部通过且无回归破坏后再同步完成。任何目标未达成都不能标记完成。

### 自检打回

按最终验收目标逐项检查。未达标或无法确认达标时先分类，只有可修复问题进入修复和复验，每项目标最多 3 次。

先分类再处理：

- 可修复：改变实施策略后修复和复验，最多 3 次。
- 需要用户验收：完成 Agent 能做的检查，再提供具体验收步骤。
- 需要用户授权或决定：立即停止相关执行，请用户选择，不消耗修复次数。
- 受阻：说明已经尝试过什么和为什么没有替代路径，不机械重试。

统一通知最小结构：

```text
{未达标 / 需要用户验收 / 需要用户授权或决定 / 受阻}

当前结果：...
原因：...
已完成：...
下一步：...
```

未达标还要说明本轮改变的策略和修复次数；需要用户操作时必须补充具体步骤和通过条件。

### 需要用户验收

Agent 无法可靠验证某项目标时，先完成自己能做的检查，再给出具体通知：

```text
需要用户验收

原因：该效果依赖真实设备上的触控体验，Agent 无法可靠判断。

验收步骤：
1. 在指定设备打开目标页面。
2. 按正常使用方式完成一次操作。
3. 重复操作三次，观察是否出现误触或卡顿。

通过条件：三次操作均完成，且没有误触、卡顿或异常跳转。

请反馈：通过或不通过；不通过时请说明出现问题的步骤和现象。
```

用户反馈前不能把该目标标记为达标。禁止只说“请自行检查”而不给步骤和通过条件。

## 典型反例

### 用完整计划代替讨论

```text
用户：开始详细讨论目录、素材和提示词。
助手：下面是完整九步计划……
```

判定：跳过逐项讨论。

### 模型建议冒充用户决定

```text
用户：目录不要复杂。
助手：默认采用 inputs/、render/、metadata/ 等分层目录……
```

判定：模型工程偏好覆盖用户约束。

### 计划只有任务名

```text
1. 修改流程。
2. 更新文档。
3. 增加测试。
```

判定：没有展示已确认决策和实施方案，也没有按用户问题组织计划。

### 验收目标扩散成施工清单

```text
1. SKILL.md 已修改。
2. 测试已增加。
3. README 已更新。
4. 版本号已同步。
```

判定：内部实施工作冒充终极目标。
