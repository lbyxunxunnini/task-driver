# 快速开始

## 30 秒选择器

按 [主协议选择器](../SKILL.md#30-秒选择器) 判断是否进入任务驱动；本页只展示环节话术与反例。

## 按需阅读

- 不清楚流程原因、状态、权限或重试规则：查看 [常见问题](faq.md)。
- 需要判断某类任务怎样讨论和验收：查看 [业务场景最佳实践](scenarios.md)。
- 需要完整协议：查看根目录 [SKILL.md](../SKILL.md)。

## 固定链路

```text
仔细询问并逐项讨论
-> 输出计划
-> 讨论并确认计划（满足全部条件时与目标合并展示）
-> 输出并确认验收目标、执行和子代理设置
-> 创建目标并执行
-> 未达标或无法确认达标时先分类
-> 可修复问题打回修复，最多 3 次；其他异常进入对应路径
```

## 每一步怎么说

### 逐项讨论

先整体分析当前条件下影响结果、范围、验收或风险的关键判断；已知、可查或已明确委托的自行解决，只请用户决定关键缺口，不能只收集标签或追求问遍全部参数。具体建议、例子和依据必须在正文展示；开放式直接问，确认式明确对象后直接确认，真实方案选择给选项、推荐和理由，按主协议正文交付要求使用选择器或编号选项。

```text
当前先讨论产物结构。已确认只交付动效、完整成片和生产记录，目录不能复杂。

我建议采用扁平结构：同一组产物以共同名称区分类型，放在同一目录，查找和整体交接更直接；代价是批次增多后检索压力会上升。按类型分组检索更集中，但目录层次更多。

开放了解事实：“目前通常怎样查找这些产物？”直接在正文提问。
确认理解：“我理解本次不新增目录层次，对吗？”明确对象后直接在正文确认；已有明确答案则复用，不重问。
真正比较方案时，按主协议正文交付要求展示上述结构与取舍，再用选择器或最终答复中的编号选项承载扁平结构、分类结构和自由讨论，标明推荐及理由，不重复提问。只确认结构不代表其他关键事项都已闭合。
```

整体思考相关事项，不在同一轮要求用户决定多个独立取舍；用户让模型推荐时，先承担推荐工作，不把问题退回用户。

### 结束讨论

完成领域分析、闭合关键事项后，先在正文汇总用户判断方案所需的信息，再请求结束讨论；不另加“确认汇总”的轮次。用户已要求生成计划时按主协议将汇总融入计划，不重问。

```text
我们已逐项确定：只交付动效、完整成片和生产记录，采用扁平结构，以共同名称关联同组产物。使用用户提供且已核实可用的素材，先形成可循环动效，再与已确认的音频及时间轴字幕合成；生产记录保留输入来源和参数，便于复现，不增加额外目录层次。

以上是此前讨论确认的方案。取舍是目录简单但批量检索能力有限，当前批次规模可接受；不新增素材采购、外部发布或额外交付。具体临时文件名留待实现。目前没有影响方向或完成标准的未决事项。

请选择：
1. 结束讨论并生成计划（推荐）：关键事项已经闭合，可检查具体实施方法。
2. 继续讨论：暂不生成计划，补充或调整当前判断。
```

### 输出计划

顶层计划事项对应已确认的需求或问题。每项必须包含“已确认”和“实施方案”。

```markdown
# 计划草案

任务目标：修复登录按钮错位。

## 1. 修复按钮位置

### 已确认
- 只修登录按钮，不统一其他按钮样式。

### 实施方案
调整按钮所在布局的对齐约束，保留现有视觉样式和其他按钮行为。
```

复杂任务可以增加“预期变化、涉及位置、内部验证”。不要把文件、测试和版本更新拆成新的顶层事项。

### 讨论并确认计划

用户修改时更新同一份计划。分开流程中，计划确认后先输出验收目标草案，不能直接执行。满足主协议三项合并条件时，计划和目标同轮分别展示，再统一确认，不先单独确认计划。

### 输出并确认验收目标

默认使用简短编号列表，只展示必要终极结果。

```text
1. 桌面宽度下登录按钮保持在预期位置，其他按钮样式不变。
2. 移动端窄屏下按钮保持在表单容器内，不发生横向溢出。
```

执行前提满足后，在展示验收目标的同一回复中提供三个业务选项，标明一个推荐及当前理由：

1. 执行，开启子代理：满足并发全部条件时并发实现，否则主线程执行；完成后独立审查，增加时间与资源消耗。
2. 执行，不开启子代理：主线程执行并自检，不分派执行或审查子代理，流程更轻。
3. 不执行，继续讨论：暂不执行，调整计划或目标。

用户选择执行即统一确认本轮展示的计划、目标、执行和子代理设置，不再追加同内容确认。此处不固定哪个是推荐项；实际提问必须根据任务标注。用户要求逐项确认时经第三项进入原有逐项讨论。

不设置固定条数。合并或拆分时说明对应的原始事项和原因。测试、脚本、文档和版本默认留作内部证据。

### 创建目标并执行

用户统一确认执行后，优先原样创建目标；目标工具不可用则使用计划工具，两类工具均不可用才维护对话内轻量目标，再连续执行。按实际工具加载 schema、保存返回的 ID 并同步状态；完成与复审按 [主协议完成判定](../SKILL.md#完成判定与复审) 执行。

### 自检打回

开启或关闭子代理都必须先检查实际交付，完成自身能做的检查后才请求必要用户验收；可修复问题须修复后重新自检，按[异常分类](../SKILL.md#异常分类)和[完成判定与复审](../SKILL.md#完成判定与复审)处理，通知遵守[统一异常通知骨架](templates.md#统一异常通知骨架)。

示例：已确认目标是“从指定平台下载完整导出文件”；当前已提交导出，但平台停机且没有替代下载路径。

```text
受阻

当前结果：导出文件尚未下载，目标保持未完成。
原因：指定平台停机，且没有可靠替代下载路径。
已完成：已提交导出，并核实服务状态与替代路径。
下一步：停止机械重试，待平台恢复后复用原目标继续。
```

### 需要用户验收

示例的已确认目标是“手机上点击保存后，用户能看到保存成功提示”。Agent 已完成可做检查，但无法连接手机；通知必须遵守[用户验收通知格式](templates.md#用户验收通知格式)。

```text
需要用户验收

原因：Agent 无法访问手机上的实际显示结果。

验收步骤：
1. 在手机上打开保存操作所在界面。
2. 点击保存，观察是否出现成功提示。

通过条件：手机上点击保存后，用户能看到保存成功提示。

请反馈：是否看到保存成功提示；未看到时请说明实际现象。
```

用户反馈前不能把该目标标记为达标。禁止只说“请自行检查”而不给步骤和通过条件。

## 典型反例

### 没调研就把明确需求改成选择题

“1 改成 2”再问“2 还是 3”，“聊天 App”再问“App 还是网页”，均不允许。先调查分析，只有真实未决取舍才提问；事实不清自行查，不能列一串字段交给用户。

### 借审查增加权限

用户限定测试只由主线程运行，主线程不得再给审查代理写“允许重跑测试”；交付已有原始输出供核对即可。用户明确允许审查代理运行时可按原授权执行，不重复索取授权。

### 无须提问就收口

用户确认平台和形式后，业务覆盖和解决方法仍未分析，直接问“是否生成计划”属于过早收口。必须继续分析未闭合事项；同一事项停滞则补证据或给例子，不换措辞追问。

### 用计划步骤自证完成

做播放器可以有多个实现步骤，目标应验证约定播放场景实际可用；不能把步骤逐条改写成目标。若用户只要求指定“1 改成 3”，对应修改结果可以直接验收。目标少不能证明任务小；是否合并仍须满足主协议全部条件。

### 用完整计划代替讨论

```text
用户：开始详细讨论目录、素材和提示词。
助手：下面是完整九步计划……
```

判定：跳过逐项讨论。

### 模型建议冒充用户决定

```text
用户：目录不要复杂。
助手：默认采用 inputs/、render/、metadata/ 等分层目录……
```

判定：模型工程偏好覆盖用户约束。

### 计划只有任务名

```text
1. 修改流程。
2. 更新文档。
3. 增加测试。
```

判定：没有展示已确认决策和实施方案，也没有按用户问题组织计划。

### 验收目标扩散成施工清单

```text
1. SKILL.md 已修改。
2. 测试已增加。
3. README 已更新。
4. 版本号已同步。
```

判定：内部实施工作冒充终极目标。

## 禁止事项

- 禁止把待确认建议写成默认技术决策。
- 禁止模型自行结束讨论并输出计划或验收目标。
- 禁止计划缺少实施方案。
- 禁止按文件和测试膨胀顶层计划事项或最终验收目标。
- 禁止把辅助检查通过当成最终目标达成。
- 禁止在需要用户验收时只给笼统提醒，不提供步骤和通过条件。
- 禁止未经授权新建分支、提交、推送或合并。
