# 快速开始

## 30 秒选择器

可以用 [README 选择器](../README.md#30-秒选择器) 判断是否调用任务驱动。本页展示环节话术与反例。

第一次使用，先看 [一段完整交互](../README.md#最短完整流程)：描述目标 → 讨论必要取舍 → 回答是否结束讨论 → 同轮查看正式计划与验收目标 → 另行决定是否执行 → 收到经检查的结果。遇到阻塞时看本页的[受阻示例](#审查与修复)。需要时再查当前环节的话术。

## 按需阅读

- 不清楚流程原因、状态、权限或重试规则：查看 [常见问题](faq.md)。
- 需要判断某类任务怎样讨论和验收：查看 [业务场景最佳实践](scenarios.md)。
- 需要完整协议：查看根目录 [SKILL.md](../SKILL.md)。

## 固定链路

推进必须遵守[核心链路](../SKILL.md#固定链路)。下文的话术涵盖讨论与确认、同轮展示正式计划与验收目标、执行授权、实施、必需的主模型审查修复和验收。必要交付、验收、已开启的独立复核与最终完成条件由主控统一维护。

## 每一步怎么说

### 逐项讨论

必须按[决策项与提问](discussion.md#决策项与提问)先交付能形成的建议，并在正文展示具体建议、例子和依据。必须只问仍需用户输入的事项。用户明确要求逐项讨论时，必须按其要求组织，并按主协议使用选择器或编号选项。

```text
当前先讨论产物结构。已确认只交付动效、完整成片和生产记录，目录不能复杂。

我建议采用扁平结构：同一组产物以共同名称区分类型，放在同一目录，查找和整体交接更直接；代价是批次增多后检索压力会上升。按类型分组检索更集中，但目录层次更多。

开放了解事实：“目前通常怎样查找这些产物？”必须直接在正文提问。
确认理解：“我理解本次不新增目录层次，对吗？”必须明确对象后直接在正文确认；已有明确答案则必须复用，禁止重问。
真正比较方案时，必须按主协议在正文展示上述结构与取舍，再用选择器或最终答复中的编号选项承载扁平结构、分类结构和自由讨论，并标明推荐及理由。禁止重复提问或把结构确认扩大为所有事项已闭合。
```

必须整体分析相关事项，说明同场景方案中可分别修改的部分。禁止夹带无关决定。用户让模型推荐时，模型必须先给出推荐，禁止把推荐责任退回用户。

### 信息充分而不冗余的示例

已核实旧配置有定时构建，用户要先恢复 Jenkins；是否保留定时触发尚未决定：

```text
助手：旧配置包含定时构建，恢复后可能在无人操作时触发。我建议先手动构建，便于核对新机结果；代价是暂时没有定时构建。你希望先只手动，还是保留定时触发？
```

反例：“建议先手动，确定吗？”没有说明已知事实及取舍；另一反例是重复讲述整个迁移背景，却没有提出当前问题。若是否会自动触发尚未核实，必须先核查或标明未知，禁止当作事实。

### 连续深挖示例

下面只展示三个连续回合，不代表该任务全部讨论完毕。环境资料已核实：旧 Jenkins 有定时构建配置；当前用户要先恢复 Jenkins 并跑通 iOS。

```text
助手：旧配置里保留了定时构建，直接恢复可能在无人操作时启动任务。
我建议先只允许手动构建，方便先核对新机结果；代价是暂时没有定时构建。
本轮的构建触发方式选择：1. 仅手动（推荐） 2. 恢复原定时触发 3. 继续讨论。
用户：先只手动。

助手：已确定仅手动触发。旧流水线还会在构建成功后上传产物；
手动触发并不意味着取消上传。我建议本轮先保留本地包，避免验证包自动外发，
但需要你自行取包。本轮是否保留构建成功后的自动上传？
1. 不自动上传（推荐） 2. 保留原上传 3. 继续讨论。
用户：不上传，存在本机。文件名你定。

助手：已确定包留在本机，不自动上传；文件名由我决定。
我会使用版本号和构建序号，例如 App-1.2.0-42.ipa，方便区分多次构建。
接下来继续核对其他仍需你决定的事项。
```

文件名已由用户明确委托，模型必须在委托范围内决定，禁止继续追问或把该委托扩大到其他事项。未委托时，必须根据已有要求、项目惯例及实际交付影响判断是否需要用户决定。禁止遗漏真实且需用户决定的细小偏好，也禁止仅因能选择就单独提问。通知、覆盖策略等若仍相关且未决，必须留待后续按必要性讨论，禁止由上述回答一并确认。

### 结束讨论

完成领域分析并通过覆盖与决定核对后，必须先在正文汇总用户判断方案所需的信息。没有待决项时，必须按[入口规则](../SKILL.md#接到任务后的第一步)和[状态检查](workflow-control.md#首次从讨论转入计划)实际发出收口问题，即使用户此前已要求给出计划。发问后必须停在讨论阶段，等待针对该问题的明确肯定答复。禁止另加“确认汇总”的轮次。

```text
我们已逐项确定：只交付动效、完整成片和生产记录，采用扁平结构，以共同名称关联同组产物。使用用户提供且已核实可用的素材，先形成可循环动效，再与已确认的音频及时间轴字幕合成；生产记录保留输入来源和参数，便于复现，不增加额外目录层次。

以上是此前讨论确认的方案。取舍是目录简单但批量检索能力有限，当前批次规模可接受；不新增素材采购、外部发布或额外交付。已沿素材输入、生成、合成、交付与失败处理核对相关决定，没有遗漏的待决用户取舍；内部临时文件名不影响交付，留待实现。

当前覆盖与决定核对已通过，推荐结束讨论并开始整理具体实施方法；如果你仍有补充，也可以继续讨论。

是否结束讨论并开始展示正式计划与目标？
```

这句话是推荐示范，可以用其他等效表达。覆盖与决定核对必须通过，必须没有阻塞待决项，正文最后必须只问一个问题，且 `semantic_review` 必须确认该问题确实在询问是否结束讨论并展示正式计划与目标。

### 同轮展示计划和验收目标

收到用户对收口问题的明确肯定答复后，必须同轮展示正式计划与验收目标。顶层计划事项必须对应已确认的需求或问题，每项必须包含“已确认”和“实施方案”。

```markdown
# 计划草案

任务目标：修复登录按钮错位。

## 1. 修复按钮位置

### 已确认
- 只修登录按钮，不统一其他按钮样式。

### 实施方案
调整按钮所在布局的对齐约束，保留现有视觉样式和其他按钮行为。

### 执行步骤
1. S1 [pending] 调整按钮位置与宽度约束，并记录实际差异。
2. S2 [pending] 检查桌面和窄屏布局，附验证证据。

# 验收目标

G1 [changed] 登录按钮在桌面和移动端窄屏下均保持在预期位置、无横向溢出；来源：用户要求只修登录按钮。

明确排除：
E1 其他按钮样式调整；来源：用户要求只修登录按钮。
```

复杂任务可以增加“预期变化、涉及位置、内部验证”。用户修改时，必须更新同一份计划。验收目标必须按 `included`、`excluded`、后续 `evidence_map` 和内部范围快照 `goal_scope_baseline` 组织，必须限于改动直接结果和直接关联结果。

同轮展示计划和目标后，必须按[主控展示策略](../SKILL.md#展示与确认策略)核对内容确认、委托或内容确认豁免。开始执行前，必须取得用户对已展示范围的明确执行授权。展示后的同一条回复可以确认多项，见[完整交互](../README.md#最短完整流程)。

禁止设置固定条数。合并或拆分时必须说明对应的原始事项和原因。测试、脚本、文档和版本默认留作内部证据。

### 创建目标并执行

有效内容确认与执行授权齐备后，必须按宿主限制复用或创建目标。宿主 Goal 可用时禁止降级。只有实际工具或宿主证据证明不可用时，才可按降级流程办理；继续前必须先说明情况并取得用户对计划或对话编号跟踪的确认。使用宿主工具时必须加载实际工具的 schema、保存返回的 ID 并同步状态。完成与复审必须按 [主协议完成判定](../SKILL.md#完成门槛) 执行。

### 审查与修复

主模型必须审查实际交付。发现问题必须先[分类](../references/review.md#异常分类)，禁止将不可修复的问题纳入修复循环。修复后必须重新审查，最后一次修复也必须复验。独立首审可先复核待交付内容，实际交付和必要验收必须另取证。未开启子代理仍必须满足[共同完成条件](../SKILL.md#完成门槛)。异常通知必须遵守[统一骨架](templates.md#统一异常通知骨架)。

示例：已确认目标是“从指定平台下载完整导出文件”；当前已提交导出，但平台停机且没有替代下载路径。

```text
受阻

当前结果：导出文件尚未下载，目标保持未完成。
原因：指定平台停机，且没有可靠替代下载路径。
已完成：已提交导出，并核实服务状态与替代路径。
下一步：停止机械重试，待平台恢复后复用原目标继续。
```

### 需要用户验收

示例的已确认目标是“手机上点击保存后，用户能看到保存成功提示”。Agent 已完成可做检查，但无法连接手机；通知必须遵守[用户验收通知格式](templates.md#用户验收通知格式)。

```text
需要用户验收

原因：Agent 无法访问手机上的实际显示结果。

验收步骤：
1. 在手机上打开保存操作所在界面。
2. 点击保存，观察是否出现成功提示。

通过条件：手机上点击保存后，用户能看到保存成功提示。

请反馈：是否看到保存成功提示；未看到时请说明实际现象。
```

用户反馈前禁止把该目标标记为达标。禁止只说“请自行检查”而不给步骤和通过条件。

## 典型反例

### 没调研就把明确需求改成选择题

用户已明确“1 改成 2”或“聊天 App”时，禁止再问“2 还是 3”或“App 还是网页”。必须先调查分析并自行核实可查事实，必须只问仍需用户决定的真实取舍。禁止把一串待核实字段交给用户。

### 借审查增加权限

用户限定测试只由主线程运行时，禁止向审查代理写“允许重跑测试”或以其他方式授予该权限。必须用已有原始输出供审查核对。用户已明确允许审查代理运行时，可以按原授权执行，禁止重复索取授权。

### 无须提问就收口

用户确认平台和形式后，业务覆盖和解决方法仍未分析时，禁止直接问“是否生成计划”。必须继续分析未闭合事项。同一事项停滞时，必须补证据或给例子，禁止只换措辞追问。

### 用计划步骤自证完成

做播放器可以有多个实现步骤，目标必须验证约定播放场景实际可用。禁止把步骤逐条改写成目标。若用户只要求指定“1 改成 3”，对应修改结果可以直接验收。禁止用目标数量少证明任务小；合并仍必须满足主协议全部条件。

### 用完整计划代替讨论

```text
用户：开始详细讨论目录、素材和提示词。
助手：下面是完整九步计划……
```

判定：跳过逐项讨论。

### 模型建议冒充用户决定

```text
用户：目录不要复杂。
助手：默认采用 inputs/、render/、metadata/ 等分层目录……
```

判定：模型工程偏好覆盖用户约束。

### 计划只有任务名

```text
1. 修改流程。
2. 更新文档。
3. 增加测试。
```

判定：没有展示已确认决策和实施方案，也没有按用户问题组织计划。

### 验收目标扩散成施工清单

```text
1. SKILL.md 已修改。
2. 测试已增加。
3. README 已更新。
4. 版本号已同步。
```

判定：内部实施工作冒充终极目标。

## 禁止事项

- 禁止把待确认建议写成默认技术决策。
- 首次收口与正式展示必须遵守上文[结束讨论](#结束讨论)和[同轮展示计划和验收目标](#同轮展示计划和验收目标)的条件。取得对收口问题的明确肯定答复前，禁止展示正式计划或验收目标。
- 禁止计划缺少实施方案。
- 禁止把文件、测试和版本更新拆成新的顶层计划事项，禁止按文件和测试膨胀最终验收目标。
- 禁止把辅助检查通过当成最终目标达成。
- 禁止在需要用户验收时只给笼统提醒，不提供步骤和通过条件。
- 禁止未经授权新建分支、提交、推送或合并。
