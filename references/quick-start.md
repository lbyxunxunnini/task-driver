# 快速开始

## 30 秒选择器

按 [主协议选择器](../SKILL.md#30-秒选择器) 判断是否进入任务驱动；本页只展示环节话术与反例。

## 按需阅读

- 不清楚流程原因、状态、权限或重试规则：查看 [常见问题](faq.md)。
- 需要判断某类任务怎样讨论和验收：查看 [业务场景最佳实践](scenarios.md)。
- 需要完整协议：查看根目录 [SKILL.md](../SKILL.md)。

## 固定链路

```text
仔细询问并逐项讨论
-> 输出计划
-> 讨论并确认计划（满足全部条件时与目标合并展示）
-> 输出并确认验收目标、执行和子代理设置
-> 创建目标并执行
-> 未达标或无法确认达标时先分类
-> 可修复问题打回修复，最多 3 次；其他异常进入对应路径
```

## 每一步怎么说

### 逐项讨论

先按场景指南完成必要调研分析；有关键取舍才请用户决定当前项，不能只根据需求关键词问问题。选择题说明各项影响、推荐和理由，有可用原生选择器则调用，保留自由讨论入口。

```text
当前先讨论产物结构。

已确认最终只需要动效、完整成片和生产记录，并且目录不能复杂。
我的建议是采用扁平结构……优点是……代价是……

请选择：
1. 采用扁平结构（推荐）：满足已确认产物要求，目录简单。
2. 按产物类型分组：检索更集中，但增加目录层次。
3. 自由讨论或调整建议：当前不确定结构，先讨论。
```

不要在同一轮顺带展开素材来源、提示词、字幕和校验方法。

### 结束讨论

完成问题与解决方向分析、闭合关键事项后才可请求结束讨论；无须提问不能作为充分依据。用户已要求生成计划时按主协议直接输出，不重问。

```text
已确认仅交付动效、完整成片和生产记录，采用扁平结构，素材来源和合成方法也已逐项确认；没有影响方案或完成标准的未决事项。

请选择：
1. 结束讨论并生成计划（推荐）：关键事项已经闭合，可检查具体实施方法。
2. 继续讨论：暂不生成计划，补充或调整当前判断。
```

### 输出计划

顶层计划事项对应已确认的需求或问题。每项必须包含“已确认”和“实施方案”。

```markdown
# 计划草案

任务目标：修复登录按钮错位。

## 1. 修复按钮位置

### 已确认
- 只修登录按钮，不统一其他按钮样式。

### 实施方案
调整按钮所在布局的对齐约束，保留现有视觉样式和其他按钮行为。
```

复杂任务可以增加“预期变化、涉及位置、内部验证”。不要把文件、测试和版本更新拆成新的顶层事项。

### 讨论并确认计划

用户修改时更新同一份计划。分开流程中，计划确认后先输出验收目标草案，不能直接执行。满足主协议三项合并条件时，计划和目标同轮分别展示，再统一确认，不先单独确认计划。

### 输出并确认验收目标

默认使用简短编号列表，只展示必要终极结果。

```text
1. 桌面宽度下登录按钮保持在预期位置，其他按钮样式不变。
2. 移动端窄屏下按钮保持在表单容器内，不发生横向溢出。
```

计划、目标和必要授权都明确后，只提供三个业务选项，标明一个推荐及当前理由：

1. 执行，开启子代理：满足并发全部条件时并发实现，否则主线程执行；完成后独立审查，增加时间与资源消耗。
2. 执行，不开启子代理：主线程执行并自检，不分派执行或审查子代理，流程更轻。
3. 不执行，继续讨论：暂不执行，调整计划或目标。

用户选择执行即统一确认本轮展示的计划、目标、执行和子代理设置，不再追加同内容确认。此处不固定哪个是推荐项；实际提问必须根据任务标注。用户要求逐项确认时经第三项进入原有逐项讨论。

不设置固定条数。合并或拆分时说明对应的原始事项和原因。测试、脚本、文档和版本默认留作内部证据。

### 创建目标并执行

用户统一确认执行后，原样创建目标或维护轻量目标，再连续执行。工具 schema 未加载先精确加载；保存 ID，开始时同步执行中；完成与复审按 [主协议完成判定](../SKILL.md#完成判定与复审) 执行。

### 自检打回

自检必须按[异常分类](../SKILL.md#异常分类)和[完成判定与复审](../SKILL.md#完成判定与复审)处理，通知遵守[统一异常通知骨架](templates.md#统一异常通知骨架)。

示例：已确认目标是“从指定平台下载完整导出文件”；当前已提交导出，但平台停机且没有替代下载路径。

```text
受阻

当前结果：导出文件尚未下载，目标保持未完成。
原因：指定平台停机，且没有可靠替代下载路径。
已完成：已提交导出，并核实服务状态与替代路径。
下一步：停止机械重试，待平台恢复后复用原目标继续。
```

### 需要用户验收

示例的已确认目标是“手机上点击保存后，用户能看到保存成功提示”。Agent 已完成可做检查，但无法连接手机；通知必须遵守[用户验收通知格式](templates.md#用户验收通知格式)。

```text
需要用户验收

原因：Agent 无法访问手机上的实际显示结果。

验收步骤：
1. 在手机上打开保存操作所在界面。
2. 点击保存，观察是否出现成功提示。

通过条件：手机上点击保存后，用户能看到保存成功提示。

请反馈：是否看到保存成功提示；未看到时请说明实际现象。
```

用户反馈前不能把该目标标记为达标。禁止只说“请自行检查”而不给步骤和通过条件。

## 典型反例

### 没调研就把明确需求改成选择题

“1 改成 2”再问“2 还是 3”，“聊天 App”再问“App 还是网页”，均不允许。先调查分析，只有真实未决取舍才提问；事实不清自行查，不能列一串字段交给用户。

### 借审查增加权限

用户限定测试只由主线程运行，主线程不得再给审查代理写“允许重跑测试”；交付已有原始输出供核对即可。用户明确允许审查代理运行时可按原授权执行，不重复索取授权。

### 无须提问就收口

用户确认平台和形式后，业务覆盖和解决方法仍未分析，直接问“是否生成计划”属于过早收口。必须继续分析未闭合事项；同一事项停滞则补证据或给例子，不换措辞追问。

### 用计划步骤自证完成

做播放器可以有多个实现步骤，目标应验证约定播放场景实际可用；不能把步骤逐条改写成目标。若用户只要求指定“1 改成 3”，对应修改结果可以直接验收。目标少不能证明任务小；是否合并仍须满足主协议全部条件。

### 用完整计划代替讨论

```text
用户：开始详细讨论目录、素材和提示词。
助手：下面是完整九步计划……
```

判定：跳过逐项讨论。

### 模型建议冒充用户决定

```text
用户：目录不要复杂。
助手：默认采用 inputs/、render/、metadata/ 等分层目录……
```

判定：模型工程偏好覆盖用户约束。

### 计划只有任务名

```text
1. 修改流程。
2. 更新文档。
3. 增加测试。
```

判定：没有展示已确认决策和实施方案，也没有按用户问题组织计划。

### 验收目标扩散成施工清单

```text
1. SKILL.md 已修改。
2. 测试已增加。
3. README 已更新。
4. 版本号已同步。
```

判定：内部实施工作冒充终极目标。

## 禁止事项

- 禁止把待确认建议写成默认技术决策。
- 禁止模型自行结束讨论并输出计划或验收目标。
- 禁止计划缺少实施方案。
- 禁止按文件和测试膨胀顶层计划事项或最终验收目标。
- 禁止把辅助检查通过当成最终目标达成。
- 禁止在需要用户验收时只给笼统提醒，不提供步骤和通过条件。
- 禁止未经授权新建分支、提交、推送或合并。
