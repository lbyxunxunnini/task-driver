# 目标设计

输入：用户需求与有效决定、计划和约束。输出：最终目标、通过条件及必要证据类型。目标必须来自需求，计划只用于交叉核对。每个计划项必须服务已确认需求或目标，每个目标必须有实施路径和可行的验证依据。缺覆盖时必须补计划；额外工作必须删除或先讨论。禁止从自选施工步骤反推目标。目标自身有取舍时，必须交回讨论；展示和确认由[主控](../SKILL.md#展示与确认策略)负责。

## 输出并确认验收目标

目标用于定义用户需要的最终结果。正式展示由主控安排；分析阶段必须考虑结果如何验证，禁止等实施完成才补标准。

### 问题与目标映射

目标必须描述已确认需求对应的最终结果。多个步骤可服务同一结果；相同结果可合并，能独立成败的必要结果可拆分，合并或拆分必须说明来源和原因。禁止按文件、模块、测试场景或实施步骤拆目标。

原问题未解决时，禁止因计划做完而判定目标达成。直接验收指定修改本身，必须有用户明确把该修改作为交付要求。能力任务必须验证约定场景实际可用。禁止仅凭目标数量少判定任务规模小。

会改变结果、范围或风险的未决取舍，必须作为缺口交回主控。

目标展示或宿主目标创建后，用户明确变更范围、排除外部依赖或接受部分结果时，必须以最新要求作为业务验收口径。旧目标及替代关系必须按[目标范围变化与旧目标失效](execution.md#目标范围变化与旧目标失效)保存和同步；旧目标禁止继续作为完成判定依据。宿主支持更新、需要用户决定替换或完全无法维护时，必须按该节对应分支处理。

没有 Goal 模式时，当前目标和 `superseded_goals` 必须保留同一稳定的 `local_goal_id`。`host_id` 的处理和宿主状态报告必须遵循[旧目标记录规则](execution.md#目标范围变化与旧目标失效)。

宿主 Goal 可用时，必须记录实际 `goal_tracking_host_id` 和 `goal_tracking_host_receipt`。改用 `plan` 或 `conversation` 跟踪时，必须满足[宿主目标工具协议](execution.md#宿主目标工具协议)的降级条件，并保存稳定的 `goals.local_goal_id`、`goal_tracking_fallback_reason`、`goal_tracking_fallback_evidence` 和用户确认来源。禁止以展示、确认或局部编号步骤冒充宿主目标创建。

### 最小必要目标

每个候选目标都必须做删除判断：删去后仍能认定对应问题完全解决的，必须删除或降为内部检查。

必须把宽泛要求转成可观察的结果。写入验收草案前，必须逐项配对可独立判断的条件及其依据，正文和现有 `source` 的归属必须一致。

| 条件怎样确定 | 来源怎样写 |
|---|---|
| 用户原话或适用规则已经支持该具体条件 | 必须引用实际消息或规则，保留原来的对象、数字和限制 |
| 由模型在有效委托内决定 | 必须写明做法、委托的具体范围及消息来源 |
| 对验收确有必要的模型建议 | 必须在该条件旁标「建议，待确认」并交代作用，随整体方案一起评审 |
| 为编排、样式或施工方便而选择的参数 | 必须放进计划的实施方案，可随方案调整 |

例如，用户说「给我一份简短的主持流程」，验收结果可写为「交付简短且可直接使用的主持流程」，来源引用该用户要求。「控制在一页内」若只是排版选择，写进实施方案；若确实需要用它界定验收，则写「一页内（模型建议，待确认）」。同一目标里有不同来源时，必须按条件标注。用户整体确认且实际覆盖该条件时，必须在目标确认门槛保留确认消息并沿用各条件的原始来源；仅肯定方向或部分条件时，其余建议必须保留待确认。创建宿主目标和执行前，必须只使用用户已确认或有有效委托的条件。

通过条件必须对应当前交付对象。只交方案、稿件或原型时，建议的试行或效果追踪必须列为后续安排。用户要求实际效果时，必须保留相应实施与验证。用户仅限定本轮展示计划时，整体目标仍必须按任务请求确定，本轮展示按[主控](../SKILL.md#展示与确认策略)处理。

必须按用户已确认的使用结果和明确约束解释“整体大致一致”等宽泛要求，禁止自动纳入参考材料中的所有用法。自拟条件缺少范围依据却已列入待办时，必须直接撤下，并在本轮用一句话说明原约定验什么、撤下哪项及缺少什么范围依据，禁止把撤下项写入 `excluded`。禁止删除用户已确认或后来新增的结果；两种已约定的操作相互破坏、有证据的必要回归，仍必须按原目标处理。询问前必须确认不清之处会改变用户要的核心结果，且无法从材料确定。

目标必须对应用户可见或可复查的最终状态，能判断达成、未达成或受阻，必要时必须包含失败或降级结果。禁止用“完善、优化、支持好”等模糊词隐藏范围、产物或技术决定。测试、脚本、文档、版本成为目标必须有用户明确要求将其作为最终交付，否则必须只作内部证据。

### 目标拆分与证据映射

验收目标必须在 `goals` 中拆成三个明确部分：

- `included`：本次纳入验收的目标项。每项必须记录稳定 `id`、`kind`、`criterion` 和 `source`。`kind` 必须为 `changed`（实际改动直接产生的结果）或 `associated`（由改动直接影响的关联结果）。禁止加入无关能力、完整产品链路或仅属计划的施工步骤。
- `excluded`：用户明确排除的验收项。必须先核实用户原话直接指明的排除对象或已确认的排除清单，再按原范围记录稳定 `id`、`item` 和来源。没有依据时禁止生成该项。“只要某交付物”限定交付对象，“轻量”等说明程度；禁止凭这些要求枚举用户未明确排除的能力。模型自行不做的事项必须在实施方案说明，禁止填入此处。必须保留已明确排除的项目；本次改动造成的回归必须按[统一范围判断](review.md#审查发现的范围判断)处理。
- `evidence_map`：必须按 included 的 `id` 记录已取证且能支持通过条件的实际结果，每项必须是一组[证据记录](verification.md#执行验证)。默认按证据收口时，每个 included 都必须有可核对记录，且覆盖所有必要条件。禁止填入 excluded。旧字符串引用可保留为线索，计入本次完成前必须核实实际来源和观察。

`goals.presented` 为真时必须同时存在 `included`、`excluded` 和 `evidence_map`。没有用户明确排除项时，`excluded` 必须是空列表；尚未取证时，`evidence_map` 必须是空对象 `{}`。拟验证方式必须写在计划步骤或正文的“验证方式”，禁止当作实际证据。已有真实证据必须按实际覆盖保留，范围变化时必须重核适用性，禁止为套初次展示格式清空有效证据。按证据收口前必须补齐覆盖；证据必须说明验证方式和实际观察结果，禁止只写“已测试”或复用无关目标的证据。

必须用 `goal_scope_baseline` 保存最后一次已确认目标的 included/excluded 快照。初次展示时该快照必须与当前范围一致；中途隐藏目标时必须保留旧快照，禁止因 `presented:false` 丢掉旧范围。范围变化且取得来源后必须更新快照。脚本用它识别“旧目标 A → 隐藏 → 新目标 B”的跨轮变更。

用户改变 included、excluded 或验收范围时，必须按新要求形成新目标并记录实际确认来源，按[上文范围变更规则](#问题与目标映射)保留旧目标。禁止把已排除项继续留在 included，或仅补充 evidence_map 就重开目标确认。

完成分两种口径。默认使用 `completion_basis:evidence`，必须为所有 included 提供 evidence_map 证据。用户明确要求结束时可用 `completion_basis:user_requested`；采用此口径时，必须记录 `completion_request_source` 和 `completion_report`，其中 `verified_goal_ids` 与 `unverified_goal_ids` 必须分别对应 evidence_map 和 unverified_goals；`unverified_goals` 必须逐项写明仍未验证的 included 目标 `id`、`item`、未验证原因 `reason` 和实际影响 `impact`。禁止把用户要求结束当作目标已验证。用户要求改变目标时，必须先按上文更新目标及来源并保存替代关系，禁止按旧目标直接标记完成。

`goals` 必须只描述验收结果，逐项执行进度必须由 `plan.steps` 维护。禁止仅因步骤全部完成而认定目标达成，也禁止仅因目标已确认而标记步骤完成。


## 目标与验证约定

每项目标必须写明什么观察结果算通过、什么情况仍算失败。最终验收条件必须来自用户要求或有效委托，禁止临时抬高标准。复杂目标可有多个必要条件，宿主必须按已确认目标原样跟踪，禁止把每个检查拆成目标。用户后续可能排除的外部依赖必须记录为关联风险或待核实缺口，禁止提前作为不可撤销的完成门槛。

必须使用[目标与验证模板](templates.md#目标与验证模板)区分结果、条件和验证方式，展示与确认由主控决定。已展示的目标局部调整时，默认必须只展示新增、修改或删除的目标及其新内容和受影响的关联项；用户要求完整版本时必须全部展示。必须保留未受影响的决定和授权。用户要求逐项目标讨论时必须逐项进行并保留已有决定。
