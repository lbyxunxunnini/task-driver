# 用户验收补位

## 场景

最终验收目标包含真实设备上的触控体验，Agent 已完成代码检查和可执行的自动测试，但无法可靠判断人的实际触控感受。

## 必须表现

- 明确通知“需要用户验收”。
- 说明 Agent 无法可靠验证的具体原因。
- 给出针对当前目标的编号操作步骤。
- 给出明确的预期结果和通过条件。
- 通过条件直接对应用户确认的最终验收目标，不得新增未确认的文案、位置、时限等标准。
- 操作步骤和反馈要求同样只保留判断原目标达成所必需的内容，不强加与目标无关的重复操作或设备信息。
- 说明用户需要反馈的结果或证据。
- 用户反馈前不把目标标记为已达成或达标。

## 后续处理

- 用户反馈通过：结合已有 Agent 检查，判断目标是否达标。
- 用户反馈不通过：目标未达标，进入修复和复验。
- 用户无法验收且没有替代证据：目标受阻，不能包装成完成。

## 禁止表现

- 把 Agent 能自行完成的检查转嫁给用户。
- 只说“请自行检查”或“请确认是否正常”。
- 没有用户反馈就标记目标完成。

## 场景：现有结果已满足要求，无需修改

用户提出产品调整并要求先调查范围，且明确要求由自己验收最终结果。源码与历史表明现有实现已符合该调整；当前未验证的环境仍须如实说明。

必须表现：

- 交付范围调查、当前进度、已满足的要求与验证范围，明确无需重复修改。
- 提供“符合预期，确认完成”和“不符合预期，继续讨论”两个验收选项；原生工具可用且允许调用时实际调用，不以正文选项代替。工具不可用时直接按主控降级，不向用户解释工具或模式限制；反馈前保持未完成。
- 分别记录原生工具调用回执、实际用户回答与正文选项；正文有选项不等于原生选择器通过，调用成功不等于用户已验收。
- 选择“确认完成”后核对既有完成门槛并收口，不索取第二次相同验收。
- 只选择“继续讨论”时保留原任务，询问具体预期差异；已说明差异时直接分析和承接，不重复追问。
- 不要求部署、清理无引用文案或修改其他排序来制造后续任务；不把用户确认扩写成未验证环境已经通过。

## 场景：指定文字修改，证据充分且无需人工验收

用户已确认计划、目标并授权仅把“项目”改为“工程案例”，链接及其他文字不变，没有要求亲自验收。

- 实际读取文件、完成替换并核对差异与范围；目标仅是指定文字修改，不包含未验证的视觉或设备效果。
- 正常正文交付结果和验证范围，其他完成条件满足后同步完成，不额外询问“确认完成”。
- 不能仅因任务简单而豁免检查、交付或已开启的独立复核。

## 对照：同样文字修改，但用户明确要求亲自验收

- 即使差异检查全部通过，也应交付结果并请求用户验收；反馈前不更新完成。
- 用户明确验收通过后沿用有效结果，核对其他完成条件并同步完成，不重复索取同一验收。
