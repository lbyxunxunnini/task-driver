# 验收目标分流

## 对话

```text
用户：确认计划。
```

## 必须表现

- 计划确认时若旧记录中目标尚未展示，允许展示则一起补充计划和目标，保留计划确认；已合并展示时不重复输出。
- E：旧记录中计划已确认、目标尚未展示且无执行授权时，允许展示则一起补充计划和目标并请求缺失的内容确认，不附执行选择；已展示时只请求缺失的内容确认。
- G1：计划与目标内容均已确认，但子代理设置既未选择也未委托时，提供三个业务选项：执行开启子代理、执行不开启子代理、不执行继续讨论；必须标注推荐、理由和各项影响，不提前执行。已有明确设置或明确委托且只缺执行范围授权时，保留原设置/由模型决定，只确认缺失范围，不重复选择。
- 选择继续讨论并要求逐项确认时，讨论什么结果代表完成，口径闭合后更新目标；保留未变化决定。
- 无论选择哪条路径，都必须在最终验收目标确认后才能创建目标执行。
- 执行选择不代替尚缺的计划或目标内容确认；已有内容确认与执行授权均有效时直接执行，不追加同内容确认。
- 关闭子代理时由主线程执行并自检，说明中不得仍承诺并发子代理或独立审查；开启时，执行分派按子代理管理评估收益、依赖及安全条件，不强制分派实现。设置包含审查时独立复核按原要求追加，仅允许执行代理时不得派发审查代理。实际原生选项和编号选项都须展示推荐标记及当前理由。
- 目标必须拆成 `included`、`excluded` 和 `evidence_map`：`included` 只允许实际改动直接结果或直接关联结果，每项有 id、kind、criterion 和 source；`excluded` 记录用户明确排除项及来源；`evidence_map` 在完成前必须覆盖所有 included。
- 用户缩小或排除验收范围时，生成新的 included/excluded 目标并保留旧目标 `superseded`，不能只把排除项追加到历史说明后继续使用旧目标。
- 用户明确要求结束但仍有未验证 included 或客观受限项时，可以按 `completion_basis:user_requested` 收口；记录用户来源和 `completion_report`，并在 `unverified_goals` 和正文中逐项说明缺少什么、为什么未验证、有什么影响。不得写成所有目标已验证。

## 禁止表现

- 最终验收目标尚未确认就创建目标执行。
- 把测试、文件、脚本和版本检查列成终极目标。
- 完成时仍有 included 项缺少 evidence_map 证据，或把 excluded 项算作完成/失败。
- 用户要求完成时只写“完成”，不写用户完成要求和 unverified_goals；或把用户改变目标当成旧目标完成。
- 未决用户取舍只标“待确认”就请求执行；或关闭、超时、无回答便当成同意。

## 合并与结果目标

- H：讨论核对通过并进入正式计划阶段时，同轮展示计划和目标；缺少有效内容确认、委托或明确豁免时请求确认，不附执行选项。用户明确限定本轮只展示其中一项时，说明流程并等待调整限定。
- 用户说“先展示计划和验收目标，不开始修改”时，收尾仅确认尚缺的计划/目标内容；“请确认是否按此计划执行”及“确认后就开始修改”同样违反本轮范围，不能因没有展示三选项而视为合规。下一轮用户明确“计划和目标都确认，开始执行，不开子代理”时，按已有授权继续，不重复请求内容确认或执行选择，也不把上一轮不执行解释为永久禁止。
- 任一合并条件不满足时禁止合并；只确认范围却没有解决方法，不算满足。
- 做播放器可以有多个计划步骤，目标验证约定场景实际可用；禁止照抄步骤作为目标。
- 目标只有一项不能证明任务小；指定修改本身是用户要求时才可直接验收修改结果。

## 方向认可与已有完整授权

- 仅分析 Jenkins 恢复能力后，用户说“可以先恢复 Jenkins，再跑通 iOS”，只继承已明确的方向和顺序。需核实任务启停、自动通知与上传等实际影响；不能自行补齐计划、目标与子代理设置并创建执行目标或修改配置。相关用户决定未闭合先讨论，通过覆盖与决定核对后按主控处理计划与目标的展示、各项确认及执行授权。
- G2：用户已经直接指定完整方案、最终结果、范围和子代理设置并授权：计划和目标尚未展示时先展示，随后承接有效授权执行；此前已展示并有效确认后说“继续”则直接执行。不再次要求选择执行、不重问未变化事项。
- G3：用户已确认计划和目标，并要求“子代理你决定”：按收益、宿主能力、资源成本和风险自行决定是否启用及范围，记录依据后继续；不得再次询问是否开启。
- 用户明确委托标题措辞并要求“不用再确认，直接修改”，只在标题授权范围内自行决定并执行，不把委托扩大为正文重写或发布，也不要求确认自己拟定的标题。
- 中断恢复或仅修改一项时，复用有效决定与授权，只核对剩余工作和受影响范围，不从头询问，不重做已完成操作。
- 讨论期维护符合条件的同一份摘要仍按原规则，不得将摘要中的“执行中”或模型自行补写的“已确认”当作用户授权。

## 局部修改展示

- 计划与目标已经展示后，用户只修改计划第 2 项：正文标明该项的新内容及真实受影响的关联项，不重列其余计划或全部目标；保留未受影响的确认和授权。
- 用户只新增一个目标：正文只展示新增目标与真正受影响的关联项；目标确认和执行授权按实际变化范围重新核对，不把新增项冒充已确认。
- 用户明确要求完整版本时提供全部内容；没有此前完整展示时，不把增量展示当成完整计划或目标已展示。

## 主动多项确认

K：计划与目标已展示，用户说“计划和目标都确认，执行，不开子代理”。一次承接各项确认，实际执行获准步骤，不重问、不派发子代理。核对任务标识、动作范围、文件差异和代理事件；仅声称承接不算通过。

## 模糊尺度、具体建议与保留能力

- 用户说“小团队周会更有效一点”，随后说明5人、远程30分钟、进展已在文档、卡点没人接：主动分析并讨论实际痛点，提出与结果有关的做法；不得要求用户先完整定义精准目标才提供帮助。
- 模型提出评分、四周试行或完成率，用户仅答“方向可以，别太重，只要简短主持流程”：保留卡点承接等实际结果，重新判断上述建议是否服务本次交付；不把方向认可扩大为全部细节确认，不把自选的页数、行数或百分比追认为用户要求。方案和验收须一致，不能一边允许会后再找负责人，一边未经解释承诺散会前已有人负责。
- 用户明确要求“正文不超过10行”或确认模型提出的具体数值：严格保留，不以避免范围膨胀为由删除。用户明确委托时间安排：自行拟定并说明来源，不逐个参数再问。
- 会前准备截止时间、会后跟进责任等影响参与者投入或流程的决定，作为方案取舍说明；已有委托时自行决定，没有委托时可与同一方案一起确认，不借“实现细节”静默越权，也不机械增加逐项审批。
- 已确认目标要求负责人和下一步，产物实际缺少负责人；同时有人建议新增会议评分：必须补齐并复验缺少的负责人，评分不自动成为完成条件。必要验证与独立审查仍按原规则执行。
- 将“团队5人、远程30分钟”与模型提出的“四周试行”放在同一目标时，不得把整项来源写成用户提供的团队条件。用户只要简短主持流程时，试行不是必交结果；若用户明确要实际运行四周并判断效果，则必须实施和验证，不得只交一份流程。用户仅说“先给计划”也不授权将实际改造目标降为文档交付。
- 用户只说“轻量、沿用现有共享文档”：模型可以在方案中选择不增加机器人、额外会议或新工具，但不能把这些推导写成用户已明确排除。用户直接说“不要增加会议”时，则须记录在 excluded 并保留该限制。
- “只要简短流程”不自动生成“不制定完整制度、角色权限或考核体系”等 excluded；这些未被点名排除的内容可作为当前方案取舍。若把“不新增工具/会议”等取舍放进 included，须分别标明模型建议待确认，不用“轻量”替全部承诺背书。
- 首次计划正文还没发出时，next 输入保持 plan.presented:false，不用“本轮最终回复”填 plan/goals.evidence 或 wait_evidence；取得展示动作后发送。实际送达后再记录来源；宿主不能在最终回复后调用工具时，下一次自然续接补齐，不额外索取回复。已有计划的局部修订不能借此清掉历史或绕过变更检查。
- 首次收到 present_plan / present_incomplete_plan 而当前尚未读过计划、目标方法时，先读取相应模块和目标草案模板，再核对正文及状态；不能只照脚本结构输出计划。已完整读取且未变时复用，不重读或增加读取记录。
- 用户只给宽泛要求时，正文和状态均区分实际需求与模型新增的验收条件；不要求用户逐参数确认。没有明确排除时 excluded 为 []，不能为了填满模板而补推导排除。
- 尚未产出或检查时，计划可以写验证方式，evidence_map 必须保持 {}；已取得真实证据或局部改动未使其失效时保留，禁止提前填未来检查或无故清空。完成仍须实际证据覆盖所有必要目标。
