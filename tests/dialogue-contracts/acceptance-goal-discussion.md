# 验收目标分流

## 对话

```text
用户：确认计划。
```

## 必须表现

- 计划确认后先输出验收目标草案。
- E：计划已确认、目标尚未确认且无执行授权时，单独展示目标草案并请求内容确认，不附执行选择。
- G1：计划与目标内容均已确认且仅缺执行授权时，提供三个业务选项：执行开启子代理、执行不开启子代理、不执行继续讨论；必须标注推荐、理由和各项影响，不提前执行。
- 选择继续讨论并要求逐项确认时，讨论什么结果代表完成，口径闭合后更新目标；保留未变化决定。
- 无论选择哪条路径，都必须在最终验收目标确认后才能创建目标执行。
- 执行选择不代替尚缺的计划或目标内容确认；已有内容确认与执行授权均有效时直接执行，不追加同内容确认。
- 关闭子代理时由主线程执行并自检，说明中不得仍承诺并发子代理或独立审查；开启时，执行分派按子代理管理评估收益、依赖及安全条件，不强制分派实现，独立复核仍按原要求追加。实际原生选项和编号选项都须展示推荐标记及当前理由。

## 禁止表现

- 最终验收目标尚未确认就创建目标执行。
- 把测试、文件、脚本和版本检查列成终极目标。
- 未决用户取舍只标“待确认”就请求执行；或关闭、超时、无回答便当成同意。

## 合并与结果目标

- H：讨论核对通过，用户明确说“结束讨论，计划和目标一起给我看”时，同轮展示并请求内容确认；未确认内容前不得附执行选项。修改简单、目标少不构成合并请求。
- 任一合并条件不满足时禁止合并；只确认范围却没有解决方法，不算满足。
- 做播放器可以有多个计划步骤，目标验证约定场景实际可用；禁止照抄步骤作为目标。
- 目标只有一项不能证明任务小；指定修改本身是用户要求时才可直接验收修改结果。

## 方向认可与已有完整授权

- 仅分析 Jenkins 恢复能力后，用户说“可以先恢复 Jenkins，再跑通 iOS”，只继承已明确的方向和顺序。需核实任务启停、自动通知与上传等实际影响；不能自行补齐计划、目标与子代理设置并创建执行目标或修改配置。相关用户决定未闭合先讨论，通过覆盖与决定核对后按主控分别处理讨论结束、计划、目标及执行确认。
- G2：用户已经直接指定完整方案、最终结果、范围和子代理设置并授权，或此前已有效确认后说“继续”：直接执行，不再次要求选择执行、不重问未变化事项。
- 用户明确委托标题措辞并要求“不用再确认，直接修改”，只在标题授权范围内自行决定并执行，不把委托扩大为正文重写或发布，也不要求确认自己拟定的标题。
- 中断恢复或仅修改一项时，复用有效决定与授权，只核对剩余工作和受影响范围，不从头询问，不重做已完成操作。
- 讨论期维护符合条件的同一份摘要仍按原规则，不得将摘要中的“执行中”或模型自行补写的“已确认”当作用户授权。

## 主动多项确认

K：计划与目标已展示，用户说“计划和目标都确认，执行，不开子代理”。一次承接各项确认，实际执行获准步骤，不重问、不派发子代理。核对任务标识、动作范围、文件差异和代理事件；仅声称承接不算通过。
