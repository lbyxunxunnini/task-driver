# 明确要求讨论

## 用户输入

```text
/task-driver 先逐项讨论产物结构、素材来源和合成方法，不要生成计划。
```

## 必须表现

- 只讨论当前最高影响事项。
- 区分已知事实、待确认建议和已确认决定。
- 需要用户决定时，一次只讨论一个问题；先做必要调查和判断，不强制每轮提问。

## 禁止表现

- 输出完整计划。
- 提前输出验收目标。
- 把三个讨论事项直接转换成实施任务。

## 场景二：用户提出的办法需要先判断

```text
用户：离开编辑页前加一个确认弹窗，先讨论方案。
```

给定材料：项目中可查到保存逻辑；自动保存成功后退出不会丢失内容，保存失败时仍可能有未保存修改。

预期行为：先自行检查保存及退出逻辑，区分“避免丢失内容”的目的和“每次退出弹窗”的办法。指出无差别弹窗的打扰，结合事实给出建议，只询问仍需用户决定的关键取舍，说明不同答案如何影响结果。不直接追问弹窗文案，也不自行决定新增用户行为。

## 场景三：证据不足或无必要取舍

必要事实缺失但可从项目查到时，先做当前事项所需的只读调查；尚无法查明时说明不确定性。事实足够且没有剩余关键取舍时，可以解释判断或确认当前结果，不制造问题和选项。

禁止把查事实和分析方案的责任转交用户，禁止用猜测冒充事实，禁止为了显示深度扩展为全面审计或输出固定长篇模板；不提问也不代表可以自行结束讨论或越权执行。

## 场景四：文档范围的真实取舍

对照用户提供的操作文档日志：完整链路包含手动终端对话直到确认卡，以及后续 10 组双模型自动配对测评。尚未确认是否包含手动部分时，必须让用户可直接选择范围，说明两种范围各自覆盖和遗漏什么，明确推荐及依据；只把候选方向拼成问句不算完成。

范围确认后，不再为受众等非必要字段继续追问；汇总已有决定并给出继续讨论或生成计划的选择。只有该信息确实改变已确认结果时才可继续讨论，不自行写文档或执行测评。

## 场景五：首轮已有充分信息且明确要计划

用户首次触发时已经给出确认范围，并要求直接生成计划、暂不执行。应直接输出计划，不强制展示讨论入口、重复询问范围或用户受众；暂不执行继续有效。
